# 四工具职责与参数归属

> 本文件是 [测试台体系摸底与规划](../实验与调试体系摸底.md) 的分片。
> 批次状态、依赖与验收门槛以主文件的批次表为准；本文件只保存该部分的调研／规划原文。

## 输入、事实与判断

- **目标**：参数按对应对象与功能模块组织，用户从合理的测试界面操作，不依靠记忆配置路径、字段名或手动编辑文件。由此贯通外形／动作、单招、序列／策略、群组空间和真实地图；从正式场景也能暂停选对象，带着目标与草稿进入对应测试台并返回测试。
- **用户提出的职责与最新命名**：视觉测试台；原大型战斗实验台演进为战斗原型测试台；原小型战斗空间实验台演进为战斗空间测试台；Boss 直战升级为可选实际场景的实战测试台。画面、云、天气等也套用真实／测试场景，并使用独立参数包与场景差异。此处是目标职责，现有能力以缺口表为准。
- **约束**：编辑器启动、运行中调整、显式保存；实验与正式使用同一实现与参数来源；保持可复现与参数来源可见。
- **已证实**：大小战斗台有继承复用；泰坦陪练继承通用陪练；EnemyTuning 有统一 schema／方案；纯外形有可采样姿态。10 月 20 日新正式场景通过 CreatureCatalog／encounter 接六种生物，但旧陪练编组验证仍只接受旧图鉴，通用场景解析仍限定 `arena_id == sanctum`；泰坦参数、脑与碰撞在 `_ready()` 绑定，不具备任意修改自动重应用合同。
- **待验证**：保留真实现场同时运行独立技能预览的隔离成本；战斗技能可安全重应用的参数范围；不同真实场景的启动／导航／环境接入条件。现有场景可加载不构成这些能力已实现的证据。
- **推荐**：四个核心测试台共享一个测试工作区、对象身份与草稿；场景、敌人组、测试条件、环境参数包可组合。参数按模块归位，保持各测试环境的实际规则，按能力接入。

## 四个核心工具的职责

现存入口与统一称呼的对应如下。右列是后续沟通及目标界面命名，不代表当前运行界面已经改名或能力已经合并：

| 当前入口／源码标识 | 统一称呼 |
|---|---|
| 敌人视觉观察／实验入口 `enemy_visual_lab` | 视觉测试台 |
| 原大型战斗实验入口 `combat_lab` | 战斗原型测试台 |
| 原小型战斗空间实验入口 `combat_spatial_lab` | 战斗空间测试台 |
| Boss 直战、泰坦陪练、通用实战陪练入口 | 实战测试台下的预设与运行功能；接入前保留实际入口差异 |

画面、天气、天空、玩家、声音、导航等专项工具沿用“对应职责＋测试台”的称呼，内部先按模块归位；具体哪些独立为顶层测试台以后确定，不因参数多就不断新增台子。

| 工具 | 核心职责 | 直接产物与边界 |
|---|---|---|
| 视觉测试台 | 外形、部件、材质、配色、姿态、动作表现；固定姿态／时间轴／慢放／部位拾取 | 敌人外观与动作配置；观察与编辑的动作和正式技能共用定义。外观动作可引用技能上下文，不另存一份攻击时序或伤害数值 |
| 战斗原型测试台 | 基础战斗属性、单招形状／覆盖／前后摇／位移／阶段、技能序列与选择策略；固定目标与真人试打 | 敌人战斗配置、技能／序列方案、策略条件；保留编组引用／投放与统计，编辑编组通过入口进入战斗空间测试台 |
| 战斗空间测试台 | 研究障碍、地形、跳越／攀附／破坏、编组成员与角色分工、相对队形、组策略及空间配合 | 可复用编组模板／配置引用、组策略、投放规则与空间测试用例；不决定每关每波投入几组 |
| 实战测试台 | 选择真实／测试场景，编辑关卡／波次编排、编组份数与投放节奏／容量、玩家条件、环境；真人／自动陪练、记录／重跑、暂停选对象 | 可保存的关卡遭遇方案、测试覆盖和每轮结果；Boss 直战作为预设；编辑正式关卡与本轮试验的保存范围明确分开 |

一个参数只有一份定义和保存位置。按2026-10-21最新职责讨论，常驻编辑入口归属其专业模块；其他台显示关联值与“编辑外形／编辑技能”入口，打开同一专业编辑器，不再重复铺完整可调表。此项尚未实施，跨台编辑仍须使用同一资产／同一草稿。

视觉动作主要编辑姿态与表现；技能时序、伤害判定、实际位移和 AI 选择仍由战斗定义驱动。遇到跨域参数，另一台显示关联入口／同字段只读视图，不产生第二套编辑与数值。2026-10-21用户已认可此方向，并要求四台共同遵守下文“[四台编辑归属与统一返回](#四台编辑归属与统一返回)”；具体字段归属和导航组件仍待实施。

## 参数归属与可视编辑：整合的主线

用户本轮强调：打通工具的目的是让参数分布到对应的位置和模块，避免直接修改配置文件。参数编辑、反馈和保存是整合成果的组成部分；只增加启动页、跳转按钮或共用配置，并不能据此认定目标完成。

| 参数内容 | 主要入口与模块 | 在其他测试台出现时 |
|---|---|---|
| 敌人体型、部件、比例、材质、配色、姿态与动作表现 | 视觉测试台：对象／部位／外形／材质／动作 | 定位同一外观草稿或跳转到具体部位，不复制参数 |
| 敌人基础战斗属性、技能形状、时序、位移、伤害、冷却、阶段 | 战斗原型测试台：属性／单招／阶段／形态／时序 | 引用同一战斗方案，显示实际生效值与覆盖 |
| 单个敌人的技能序列、组合、选招条件与个体策略 | 战斗原型测试台：序列／个体策略 | 实战测试台选用或带上下文返回编辑，不与组策略混为一层 |
| 编组模板、成员数量／职责、相对队形、组策略与投放规则、障碍与空间用例 | 战斗空间测试台：编组／组策略／投放／场地／空间能力 | 其他测试台引用编组；运行创建独立组实例，地图解析实际投放位置 |
| 关卡遭遇方案、每波编组引用与份数、组间／组内节拍、人数容量、波间与 Boss、生命周期高级项 | 实战测试台：关卡编排／波次／投放／容量／高级 | 对应当前 sanctum_creatures 等数据的显式编辑入口；实际总人数派生，正式绑定与测试覆盖分开 |
| 测试地图、玩家配装、测试等级、起始阶段、种子、运行与录制条件 | 实战测试台：场景／测试方案／运行／记录 | 与敌人本体默认、正式场景绑定分别保存 |
| Sky3D、日月／时钟、云雨雪风／天气、光照／雾、后处理 | 画面／环境类测试台中的对应模块；具体顶层拆分以后确定 | 选用独立包，明确编辑共享包、本场景差异或本轮草稿 |
| 玩家近战、卫士／护盾、声音、导航与性能等已有功能 | 后续归入对应测试台／模块；复用现有面板与探针 | 统一可发现入口与参数说明，保留专门测试条件；尚未另建这些测试台 |

- 模块按“这个对象的哪一部分／这个技能的哪一阶段”组织；对象／部位拾取、搜索和关联跳转负责定位所属模块。搜索不是把所有原始字段倒进一个巨大表格。
- 配置文件仍承担底层存储和 AI／开发定位作用。日常支持范围内的参数操作必须能在界面完成读取、修改、校验、预览／重播、保存和重开确认，不把手改 JSON／Resource 作为常规流程或缺失界面的默认替代。
- 每个参数接入需说明：唯一身份与归属模块、中文名称／作用、类型／单位／范围、实际值与来源、作用目标／范围、生效时机、验证入口、保存位置／方式和支持状态。代码路径可以在详情中查，用户无需记住。
- 对应控件、数值输入／滑块、颜色／曲线／形状等可视编辑方式按内容选择；先解决已有字段的合理编辑与反馈，不要求首轮建设通用三维建模或任意动画创作软件。
- 新增参数应连同所属模块、入口、应用／保存和观察方式一起接入；否则登记为“未界面化”，不能仅因写入配置表就算交付完成。
