# 物理独立线程可行性审计

日期：2026-10-26

## 目标

判断是否值得为 `physics/3d/run_on_separate_thread=true` 改造项目里的物理空间查询。

## 查询审计

扫描 `scripts/` 与 `tools/` 中所有 `direct_space_state` / `intersect_ray` / `intersect_shape` / `cast_motion` / `intersect_point`：

- 总查询点：**95**
- 直接位于 `_physics_process` / `_integrate_forces`：9
- 直接位于输入回调：1
- 其余 85 处在辅助函数

调用图追到根后的分类：

| 类别 | 数量 | 含义 |
|---|---:|---|
| physics | 33 | 只从物理路径可达，相对安全 |
| main | 26 | 从 `_process` / 输入 / 相机调用，启用后必炸 |
| mixed | 26 | 物理和主线程都有调用，需要逐个拆 |
| unknown | 9 | 动态调用/静态入口，需要人工确认 |
| setup | 1 | `_ready` 阶段查询 |

明确在 main 路径的例子：

- `player_weapon._shot_ray`（开火命中）
- `player_melee_targets`（近战目标收集）
- `combat_fx.apply_radial_damage`（震地/手雷）
- `cinematic_action_cam` / `cinematic_kill_cam`（相机遮挡）
- `enemy_deployment.validate` / `survival_director.choose_spawn_position`（生成）
- `jump_landing` / `spatial_retreat_planner.advance`
- `sanctum_workspace._unhandled_input`

原始明细：

- `D:\Godot\lab\_tests\thread_audit\queries.json`
- `D:\Godot\lab\_tests\thread_audit\queries_context.json`

## 最小基准

探针：`tools/probes/physics_thread_benchmark.gd`

场景只有：

- 一张程序化三角网地形；
- N 个 CharacterBody3D 胶囊，中央管理器每物理帧设速度并 `move_and_slide`；
- 没有射线、导航、武器、敌人脚本。

自动化环境默认把 SceneTree 暂停，基准里每帧显式 `paused=false`，否则物理只跑 8 tick、FPS 是假高。

### 100 只

| 独立线程 | FPS（稳定段） | physics |
|---|---:|---:|
| 关闭 | 608–633 | 5.7–5.9ms |
| 开启 | 631 | 5.4ms |

差异在噪声范围内。

### 300 只

| 独立线程 | FPS | physics |
|---|---:|---:|
| 关闭 | 92–277（波动） | 18–22ms |
| 开启 | 117–304（波动） | 16–29ms |

没有稳定收益，开启后甚至出现更大的波动。

## 结论

- 独立线程**没有显著降低 physics 或提升 FPS**；主线程仍要同步、跑 `_physics_process` 回调和场景节点。
- 这个基准已经是“无查询”的上限，真实项目启用后还要面对 61+ 处查询时序改造，收益只会更小。
- **保持关闭**，不投入 PhysicsQueryService 改造。

如果未来要重开这个方向，前置条件是：

1. 先有一个真实场景基准能证明独立线程带来 >10% 帧时间收益；
2. 再把 26 处 main + 26 处 mixed + 9 处 unknown 全部改成物理帧查询/异步结果；
3. 验证射击、手雷、导航、相机、生成、场景破坏。

当前结论：不值得。
