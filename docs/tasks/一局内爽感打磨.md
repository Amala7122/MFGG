# 一局内爽感打磨

记录日期：2026-10-08（第 1、2 轮）。

## 整体目标与当前状态

目标：**只打磨"一局之内"的手感与爽感**。用户原话：「其他都可以无视，现在专心打磨就是一局内，能不能有爽感，目前还是差点意思。」

**当前状态：第 2 轮已落地，等待用户试玩。** 两轮都只动"让理论曲线和实机体验对齐"的部分，未碰伤害/血量/护盾等数值。

## 第 1 轮（已试玩反馈）

改了三处增量：战斗 HUD 恢复击杀读数 + 连杀 xN、交战中常驻"剩余 N"、出怪密度维持。

**用户第 1 轮反馈（2026-10-08）**：
1. **连杀没什么感觉** —— 理由（用户原话之意）：射击游戏里主角的移动和击杀范围不相关，站着不动也能击杀，没有"杀完一个→移动到下一个→继续杀"的连锁；动作游戏是因为不动就没法击杀。
2. **"剩余 N"没有推进感**。
3. **空场好很多**（密度维持有效）。
4. **最大的问题是体感和理论计算的割裂**：理论上应该非常轻松，实际上可能吃不到很多掉落物导致成长跟不上。**能吃上就很轻松，吃不上就比较困难。**

## 第 2 轮：按住"体感与理论割裂"这条线（已落地）

### 诊断

- **武器等级完全由"物理走过去捡到几个模块"决定**（`player_weapon.apply_upgrade` 每层 `_weapon_level += 1`），而掉落物落在**敌人的死亡位置**。敌人多半死在远处，玩家又未必敢离开掩体 → **整局的成长等于"拾取运气"**。
- 于是理论曲线（按拾取率 50%/75%/100% 推算）与实机体验直接脱钩，**同一局的手感能差一个量级**。
- 更糟的是 `spawn.extra_enemies_per_level = 7` 与掉落构成**正反馈**：捡得多→等级高→敌人更多→掉得更多→等级更高；捡得少则完全反过来。这就是"能吃上就很轻松，吃不上就比较困难"的机制来源。

### 为什么这么改

- **磁力**：把"拾取"从走位负担变成自动结算，消灭运气方差；但范围只有 11 米，所以"要不要前压到尸体附近"仍留给玩家 —— 这恰好是射击游戏里唯一能把**移动**和**击杀**绑起来的东西（也是连杀做不到的事）。
- **`extra_enemies_per_level = 0`**：切断正反馈。波次规模从此只跟"第几波"有关，玩家强度差异交给"打得更快"体现，难度曲线第一次可读。
- **撤掉连杀**：承认上一轮的设计错误。射击游戏的击杀不以位移为前提，`xN` 只是一个在跳的数字。

## 第 3 轮：卫士代捡 + 提高压力（**只做了理论计算，未改代码**）

用户提出：不要磁力拾取，改为让**浮游卫士去拾取掉落**；保证拾取后**增加敌人数量与攻击欲望**来制造更大压力，并指出主角移动太快的问题一直没动。要求先理论计算。

计算结论（完整推导见 `_artifacts/godot-ruin_star_new/in_run_feel/20261008_214500_feel/reports/wisp_salvage_and_pressure_math.md`）：

1. **卫士代捡可行但要改吞吐模型**：卫士输出只有 12.15 DPS（占玩家 0.29%~8.7%），拿去做后勤几乎不损失伤害；但它是硬绑左肩的（`floating_wisp.gd:441-457`），"去捡"是新行为。单趟搬运吞吐约 0.345 个/秒，而 L7 需要 0.68、L16 需要 1.22 → **从 L4 起追不上**。要成立必须给清扫半径（≈6 m）或大容量；给半径之后本质上就是"看得见、有延迟的磁力"。
2. **"增加敌人数量制造压力"当前不成立**，三道全局阀门让数量与威胁脱钩：远程全局 900ms 开火节流（`ranged_enemy.gd:56/464/484`）、受击无敌帧全局 0.42s（`player.gd:818`）、敌人速度 L5 封顶 7.75 < 冲刺 8.5。**敌人从 14 只加到 56 只，玩家承受 DPS 一点不变。**
3. **必须同时开四样**：`hit_invulnerability` 0.42→0.20、`damage_growth_per_level` 0.14→0.04~0.06、`ranged_global_fire_cooldown_ms` 900→350~450、敌人速度上限或 `sprint_multiplier` 1.7→1.35。外加分离力。
4. **压力应加在"场上密度"（`target_alive`）而非"每波总量"**：总量涨=打更久，密度涨=更挤且更快打完。
5. **更正第 2 轮的一处量级判断**：算上敌人血量成长后，玩家净击杀率 L1→L20 只涨约 5 倍（不是 30 倍）。故 `extra_enemies_per_level = 7` 方向没错、是**过强约 2 倍**（预算涨 4.65 倍 vs 击杀率涨 2.46 倍）；`≈3` 恰好让整局波次时长恒定，`=0` 则越来越短。0 与 3 是设计目标差异，不是对错。

**待用户决策**，未动任何代码。建议验证顺序：先试五个配置键（不改代码）看"会不会死"，再试 extra 0/3，最后才做卫士代捡（优先"清扫半径"版本）。

## 第 4 轮：修掉落物跟随 bug + 压力试验（已落地，待试玩）

用户三项指示：① 全程记录到文档，作为一个 task；② 修 bug：生命全满时加血包会跟着主角跑，掉血时又顺手吃掉（用户觉得有趣，但要求先解决，且"以后说不定有用"）；③ 修五个配置试试，**但不要动玩家移动速度**——理由是"移动慢了爽感直接降一个 level，高速移动+大量消灭才成立，沉重的移动消灭再多也很累"。

### 4.1 修 bug：用不上时就地放下（不再跟随）

- 根因：磁力在贴身（≤1.3 m）但 `_apply_to` 返回 false 时，只 `return`，**没有解除吸附**；`_magnetized` 仍为 true，于是每一帧继续把掉落物推向玩家 → 变成挂件；玩家一掉血，`try_heal` 立刻成功 → 被"顺手"吃掉。
- 修法（[pickup.gd](../../scripts/pickup.gd)）：新增 `_settled`，一旦贴身但用不上就**就地放下并退出磁力**，退回普通掉落物（继续待机浮动、可按原方式踩取）。
- **保留为开关**（回应"以后说不定有用"）：`pickup.follow_until_usable`（默认 `false`）。打开即恢复"随身补给跟着你等时机"的旧行为，并已在配置里写明那是设计而非 bug。
- 回归测试 [test_pickup_magnet.gd](../../tests/test_pickup_magnet.gd) 第 4 节扩写：满血不消耗 + 默认不跟随 + **玩家走开 60 米后掉落物位移 < 0.6 米**（即不跟随的可判定证据）。

### 4.2 压力试验：五个键

| # | 键 | 现值 → 试值 | 理由 |
|---|---|---|---|
| 1 | `player.hit_invulnerability` | 0.42 → **0.20** | 承伤上限从 2.38 次/秒抬到 5 次/秒。**这是"敌人数量"能否变成威胁的总开关**：原值下 1 只和 14 只围殴完全等价。 |
| 2 | `enemy_roster.damage_growth_per_level` | 0.14 → **0.05** | 上限打开后，后期单次伤害若仍涨到 ×3.8，5 次/秒 = 213 DPS，0.8 秒必死。压住单次伤害，压力才来自"数量与频率"。 |
| 3 | `enemy.ranged_global_fire_cooldown_ms` | 900 → **400** | 这是 `static var` 上的**全局**闸门：全场远程兵合计每 0.9 秒只能打一发，全体远程总输出恒为 8.9 DPS。不降它，加远程兵毫无意义。 |
| 4 | `spawn.target_alive` | 6 → **10** | 压力加在"场上密度"而非"每波总量"：总量涨=打更久，密度涨=更挤且更快打完，且与武器等级无关。 |
| 5 | `enemy_roster.max_speed_growth` | 1.25 → **1.40** | 原值让最快敌人停在 7.75 < 冲刺 8.5，加多少人都只是被拉开。1.40 → 8.68（L8 达到），略高于冲刺：退着打不再是万能解，但绝大多数敌人仍追不上。 |

**明确没有改**（按用户要求）：`player.sprint_multiplier` 保持 1.7（冲刺 8.5）。压力由"敌人来追"实现，不由"玩家变慢"实现。这个取舍已写进配置注释，避免以后有人按常规思路去降移速。

本轮同时未做：敌人分离力（`nav_steering` 邻居斥力）。它是密度的前提（否则 10 只叠成一坨），但属于代码改动，留到下一步。

## 第 5 轮：试玩反馈修正（已落地，待再试玩）

### 用户反馈原文之意

1. **敌人投放数少了很多，完全没压力。**
2. **基本没弹幕。**
3. **近战怪可能是硬直时间太久了，基本被打就是木桩。**
4. **主角弹道散射虽然准确，但心理感受很不好，跟天女散花一样**；又因为射速快、敌人硬直长，**近距离高速射击成了最佳选择** —— "用着冲锋枪，弹道像散弹"。

### 逐条查出真正原因（含对第 3 条的更正）

**① 敌人少 —— 是我上一轮改错了。**
`spawn.extra_enemies_per_level = 0` 把每阶段总量锁死为 sanctum 的 11/15/19/23 = **68 只**（原先在 L16 时约 200+）。当时改它的理由是"敌人变多只等于打更久"，但那个前提是承伤上限（0.42）与远程节流（900ms）**都还关着**；第 4 轮把两道阀门打开之后，"更多敌人"才第一次等于"更难"。
→ `extra_enemies_per_level` **0 → 8**，`max_alive` 14 → **18**。

**② 没弹幕 —— 因为 `enemy_mix.ranged_ratio` 是死配置。**
全项目零读取点（台账 I-017），远程占比实际只由"解锁了几条远程条目"决定：L1 池 1/3、L3 池 4/11。sanctum 配的 0.42、沙丘配的 0.58、内城配的 0.24 **全部无效**。敌人又少，所以场上通常只有两三只远程 → 看起来没有弹幕。
→ `wave_director._pick_entry()` 改为**先按 `enemy_mix.ranged_ratio` 掷 kind，再在组内按 weight 抽**（新抽 `_pick_weighted()`；arena 没配则用 `spawn.ranged_ratio` 兜底）。

**③ 木桩 —— 不是硬直，是"走不到"。**
核对结果：**普通子弹不会造成任何硬直**。`apply_push()`（会写 `_stagger_time`）的调用方只有 `combat_fx.apply_radial_damage`（手雷 / Q 震地脉冲）与 `resonance`；`take_damage()` 只调 `_rig.flinch()`，而 `flinch()` 只改视觉冲击值，**不打断攻击、不停止移动**。
真正原因在投放与接近速度：
- `enemy_deployment.validate()` 强制落点距玩家 **14~32 米**；
- 近战兵基础速度约 4.0，L1 只有 4.2 m/s → 需要 **3.3~7.6 秒**才能走到；
- 而玩家在 20 米外每秒就能打掉一只。
→ **近战怪在到达之前就死了**，看起来像木桩，也顺带解释了为什么"近距离高速射击最优"（反正敌人到不了，射程与站位不重要）。
→ 新增 `enemy.melee_approach_speed_scale`（1.8）与 `melee_approach_boost_distance`（9.0）：与玩家距离大于 9 米时接近速度 ×1.8 ≈ 7.6 m/s。**仍低于玩家冲刺 8.5**，所以"高速拉开"依旧有效，但必须真的去拉。
→ 顺带把 `enemy.stagger_duration` 0.42 → **0.28**（控制技的收益不该长到把敌人锁在原地）。

**④ 弹道像散弹 —— 持续扫射的合成散布确实太大。**
腰射 = `base + bloom + 移动比例 × movement_degrees`。持续移动扫射时约 `0.55 + 1.9 + 1.6 = 4.05°`，20 米处约 1.41 米半径 —— 机制上仍能命中（所以用户说"准确"），但视觉读起来就是一把霰弹枪。
→ `base_degrees` 0.55 → **0.25**、`movement_degrees` 1.0 → **0.35**、`max_bloom_degrees` 6.5 → **4.0**；合成散布降到约 2.7°。
→ **`bloom_per_shot` 刻意不动**：它是 `test_player_spread` 里"新旧散布模型对比"的参照项（旧模型把它乘 4.06 倍），改小会让那条回归断言失去意义。

## 第 6 轮：追回"远程狙击怪"与近失弹呼啸（已落地，待再试玩）

用户反馈之意：**"怎么没有远程狙击怪了？以前远程狙击怪是制造近失弹呼啸而过爽感的重要来源之一。"**

追查结果分两件事，**它们是两个独立的历史丢失，不是一个**。

### 6.1 狙击怪：确实被"一次修 bug"顺手删掉了

| 核对项 | 结果 |
|---|---|
| 新工程图鉴 | 远程只有 pattern 0~4（侦察射手 / 点射游骑兵 / 旋流术士 / 弹墙炮手 / 重型迫击炮），**没有 pattern 5** |
| 旧工程 `godot-ruin-star` 图鉴 | 与新版**完全一致**，也没有 pattern 5 |
| 主场景 15 个固定刷怪点 | `ranged_pattern` 只有 0~4 |
| 狙击机制本体 | **完整存在**：`ranged_enemy.gd` 的 SNIPER 分支、`sniper_bullet.gd`（72 m/s 重弹）、`telegraph.gd` 的锁定红线、`skill_limiter` 的 `sniper_lock` 限流 |

丢失过程有记录（`_analysis/PACKAGE-LOG.md`）：移植包 A 版的狙击判定用的是**标题启发式**（`enemy_title.contains("游骑兵")`），于是「点射**游骑兵**」会被当成狙击兵——**这正是用户记忆里的"远程狙击怪"**。后来为修这个误判，改成"只认 `pattern_type == 5`"，**却没有任何条目配 5** → 狙击行为彻底消失，而且没有任何检查会报出来。

## 第 7 轮：满武器压力（TTK 塌陷）与近失声效响度（已落地，待再试玩）

### 7.1 压力：数量不是杠杆，**击杀耗时（TTK）才是**

95 只怪是在武器约 L13 时出现的（`23 + 8×(L-4) = 95`）。查下来问题不在数量：

| 等级 | 近战兵血量（旧） | 玩家实际 DPS（模型值×命中/装填折损） | TTK |
|---|---|---|---|
| L1 | 122 | ~70 | 1.75 s |
| L4 | 216 | ~248 | 0.87 s |
| L10 | 405 | ~753 | 0.54 s |
| **L13** | **500** | **~1225** | **0.41 s** |

而敌人从 **14~32 米**外投放，按接近速度（含上一轮的 1.8 倍加速）也需要 **2~4 秒**才能贴到玩家。
**TTK 0.41 秒 ≪ 接近 3 秒 —— 敌人永远死在路上。** 加数量只是把队列拉长，不会变成压力；近战"像木桩"也是同一根因。

根因是**两条成长曲线不匹配**：`health_growth_per_level = 0.35` 是**线性**的，而玩家输出随等级近似**指数**（等级曲线 + 模块乘区，L13 约 19 倍）。线性吃不掉指数。

→ 新增 `enemy_roster.health_growth_compound`（**1.08**）：近战血量 = `base × (1 + 0.35L) × compound^(L-1)`。
   - **只作用于近战**；远程仍走 `health_tier` 档位表，避免破坏"狙击几发打死"的契约。
   - 复利后 TTK（模型口径）：L1 1.75 s、L4 1.10 s、L7 1.02 s、L10 1.08 s、L13 1.03 s、L20 1.46 s —— **基本恒定**。
   - `1.0` 即关闭、恢复纯线性。开机偏肉用 1.06，后期偏软用 1.10。
→ `spawn.target_alive` 10 → **14**、`refill_interval` 0.35 → **0.25**。敌人现在活得久了，密度才第一次有意义（此前它们 0.4 秒就没了，密度维持只是在补一群立刻消失的人）。

### 7.2 音效：你没记错，但也不是改差了 —— 是**相对响度**变了

| 核对项 | 结果 |
|---|---|
| 合成音色规格 | 与旧工程**逐字节相同**（`bullet_whiz: [0.16, 1500→310Hz, 4.2, 0.42, 0.85]`） |
| 声部池 | 与旧工程相同（12 常驻 / 16 空间） |
| 播放调用 | 与旧工程 `enemy_bullet.gd` 相同（`-6.0 dB`、音高 ±8%） |
| **`audio.file_bank`** | `file_bank_enabled = true`，**但只有 2 个键**；`shot`/`sniper` 已换成**真实 WAV 采样**，`bullet_whiz`/`whoosh` 仍是**合成音色** |

所以：**同一个音，现在是躺在一堆真实枪声采样里**。`_file_gain_db` 只做"文件音源之间"的响度配平，合成音色拿不到补偿 —— 旧的 -6 dB 现场会被枪声盖住。这就是"不如以前"的直接原因。

→ `bullet_whiz` 音量 `-6.0` → **`enemy.bullet_whiz_volume_db = -2.0`**（做成配置，可继续调）。
→ 另外我上一轮**做错了一件事**：把狙击重弹的近失从 `shot` 高八度**替换**成了 `bullet_whiz`。那是替换而不是叠加 —— 单听像"轻扫一下"，反而比旧版薄。现在改成**三层叠加**：
   1. `bullet_whiz`（1500→310 Hz 扫频，破空主体）；
   2. `shot` 高八度（锐利爆音 —— **就是旧版本的那一层**）；
   3. `whoosh`（低频气流，给体量感）。
   镜头震颤维持 0.45。

## 第 8 轮：共鸣漏网 / 近失音被覆盖 / 护盾无反馈 / Q 鸡肋（已落地，待再试玩）

用户四条反馈：① 溜着近战打远程 + 攒共鸣清一波，难度不大；② **共鸣不能真的一键秒杀，总有很多漏网**；③ **近失弹完全听不到**（怀疑射击声太大）；④ **护盾没有任何视觉/受击区别**，就是一段看不见的自回血；⑤ 提议**护盾改能量、与 Q 共用槽**，被围时用震地撕开缺口，并指出震地击退与杀伤都不够。

### 8.1 共鸣"漏网"：不是随机，是 **31% 的兵种对爆发免疫**

`resonance.gd` 的即死保底 `target_dmg = maxf(target_dmg, enemy_hp + 600.0)` 原先只对 `not is_large` 生效，而 `is_large` = `scale.x >= 1.25` 或称号含巨型/重装/大型/破坏者。

图鉴 16 条里体型 ≥1.25 的正好 **5 条**（重装战士 1.35 / 大型盾卫 1.4 / 重型迫击炮 1.55 / 巨型破坏者 1.75 / 精英剑士 1.25），而且它们血量在高等级能到七八千 —— 520 点的 100% 爆发连皮都蹭不掉。**"总有很多漏网"就是这个。**

→ 改为**非 Boss 一律即死**（名副其实），Boss 仍走正常伤害公式。
→ 留开关 `resonance.instant_kill_large`（默认 `true`）：关掉即回到"只清轻装"的旧行为，方便日后觉得共鸣过强时回退。

### 8.2 近失音"完全听不到"：不是音量，是**被覆盖**

我上一轮把 `bullet_whiz` 从 -6 dB 提到 -2 dB，用户仍然完全听不到 —— 说明问题不在响度。查下来是**声道抢占**：`AudioUtil._play_at` 是**轮转 16 个 3D 声道**的（每次调用覆盖其中一个），而一次交火里命中音/格挡音每秒调用几十次，一段 0.16 秒的破空声会被下一个音效**当场截断**。

→ `audio_manager.gd` 新增**优先声道** `play_at_priority()`：一个不参与轮转的专用 3D 声道，播完为止。
→ `enemy_bullet.gd` / `sniper_bullet.gd` 的破空声改走它；音量 `-2` → **`bullet_whiz_volume_db = 4.0`**。
→ 优先声道只有一个，所以狙击那一下的三层里只有主体（破空）独占，气垫层仍走普通池（否则会自己覆盖自己）。

### 8.3 护盾没有存在感：区分"打中能量盾"与"打中身体"

原先两种情况完全一样：红色全屏闪 + 角色受击白闪。玩家感觉不到护盾挡了什么。

→ `player.gd` 里算出 `health_damage = amount - absorbed_raw`，**护盾全吸收时**：
   - 角色**不播**受击白闪（身体没被打到）；
   - HUD 改播 **能量青色短闪**（`flash_shield_hit()`，0.12 s，比红色的 0.18 s 更短更"硬"）。
→ 同一层叠加闪光复用，靠颜色与时长区分（两种情况不会同时发生）。
→ 音效区分按用户意见**先不做**。

### 8.4 震地脉冲（Q）鸡肋：击退位移只剩 2.9 米

击退位移 ≈ `push × 硬直时长 − ½×34×硬直²`。而**硬直在上一轮被我从 0.42 缩到了 0.28 秒**（为了不让控制技把敌人锁死），于是 `push 15` 只剩约 **2.9 米**，推完立刻恢复追击 —— 这正好解释了"没有很明显的击退效果"。

→ `abilities.skill.push` 15 → **30**（约 7.1 米缺口）、`damage` 55 → **120**。
→ 已注明：`enemy.stagger_duration` 会同时缩放所有击退（手雷、共鸣同理），调它要一起看。

### 8.5 关于 ① 与 ⑤（设计判断，**未实施**）

用户提的两件事其实是**同一个问题**：共鸣清场是**免费**的，所以"溜着打 + 攒共鸣"成为无风险最优解；而护盾与 Q 又各自独立、彼此无关。把**共鸣 / Q / 护盾接到同一个能量资源**上，可以一次解决三件事（共鸣免费、Q 鸡肋、护盾没存在感），但**合并方式有坑**，需要用户拍板，见回复中的三个方案。

**本轮未改动**：玩家移速（用户明确要求不动）、共鸣充能速率、护盾数值。

## 第 9 轮：Q 改成点数制（已落地，待试玩）

也就是说：点数决定"一场能用几次"，冷却决定"两次之间隔多久"，**两个闸门都要**。

### 参数（`abilities.skill`）

| 键 | 值 | 含义 |
|---|---|---|
| `charges_max` | 3 | 上限 |
| `charges_start` | 3 | **起手满点**（试玩用，方便立刻感受到"攒着三点"和"只剩一点"的差别） |
| `cooldown` | **9.0 → 3.0** | 只负责两次使用之间的最小间隔，**这就是"防止直接 3"** |
| `charge_recharge_seconds` | 16.0 | 每 16 秒回 1 点 |

**总量对照**：改动前是"每 9 秒固定一次，无限次"。现在是"前 6 秒可连放三次（第 0/3/6 秒），之后约每 16 秒回一点"。
60 秒内的总次数：旧 6.7 次 / 新约 6.5 次 —— **总量基本不变，但额度被前移到了危急时刻**，这正是"被围住能撕开缺口"想要的效果。

## 第 10 轮：重型对共鸣"该硬"，而且要有反应（已落地，待试玩）

用户判断：「**共鸣对重型敌人伤害低是应该的，否则人家白重型了**。特别是盾卫，检测到共鸣就要举盾，平时被打也应该概率举盾防御。并且重型敌人被共鸣灼烧后，物理攻击应该更强，挨得越多越强。**让共鸣也有点代价。**」

这等于撤销第 8 轮"非 Boss 一律即死"的决定，并把它升级成一个**有反应的设计**：重型不再秒杀，但会**举盾**、会**被激怒**。

### 10.1 撤销"一键清场"

`resonance.gd` 的即死保底恢复成**只对轻型生效**；过载爆发（200%）仍能秒掉重型 —— 那是"攒满再用"的回报。`resonance.instant_kill_large` 保留为开关，**默认 false**（脚本默认值也同步改成 false，避免忘记读配置时行为不一致）。

**关键点是它不再读起来像 bug**：以前"重型不死"没有任何反馈，玩家只会觉得"漏网"；现在重型会举盾、会变凶，玩家能看到"这东西扛住了"。

### 10.2 盾卫举盾

- **检测到共鸣必定举盾**：`resonance` 在**结算伤害之前**调 `on_resonance_incoming(center)` —— 顺序很关键，反应必须在伤害之前，否则"检测到共鸣就举盾"永远慢一步，减伤也就无从生效。
- **平时被打概率举盾**：`shield_raise_chance`（0.35）掷骰，受 `shield_raise_cooldown`（2.5s）限频，举 `shield_hold_seconds`（1.1s）。
- **举盾期间伤害削减 75%**，并且**触发举盾的那一下也算** —— 否则玩家会觉得"明明举起来了还是被打满脸"。
- **看得见**：盾面转到前上方（`ShieldPivot`），并在盾心打一次冷白金属火花 + `hit_metal` 音效。这是"打盾上了"与"打身体"之间唯一可靠的即时区分。
- 为此把 `enemy_profile.gd` 里盾卫的三块盾面从"直接挂肘节点"改成挂在**零偏移的 `ShieldPivot`** 下 —— 原先谁也抬不起它们。

### 10.3 重型激怒（共鸣的代价）

- 体型 ≥1.25 或称号含 巨型/重装/大型/破坏者 的敌人，**每挨一次共鸣叠一层攻击加成**（`rage_per_resonance_hit` 0.12），上限 `rage_max`（0.9），平时按 `rage_decay_per_second`（0.04/s）缓慢消退。
- 叠层直接乘在近战挥击伤害上：`(attack_damage + contact) × damage_scale × (1 + rage)`。
- **所以共鸣对重型不是没用，而是用错了会把它打得更凶** —— 这正是用户要的"代价"。

### 10.4 新增守卫

1. 100% 爆发**秒杀轻型**、**不秒杀重型**；
2. 重型仍然**吃到基础伤害**（"打不动"不等于"免疫"，且不是 `hp+600` 保底）；
3. `ShieldPivot` 存在、体型 1.4 被判为重型；
4. **检测到共鸣必定举盾**；举盾期间伤害正好被削减到 `1 - shield_damage_reduction`；不举盾时吃满；
5. 激怒**叠层、封顶**，且**非重型不涨**。

### 10.5 已知边界

## 第 11 轮：盾卫插盾防御姿态（攻防相位，手雷成为正解）（已落地，待试玩）

用户细化要求：「**盾卫举盾需要把盾插地做防御姿态，解除需要时间，但是防御时可以转向**；玩家想打，**扔手雷炸他**，正好让手雷有点用。」

这等于把第 10 轮的"抬一下手"升级成一套**有起手、有持续、有解除的相位**。

### 11.1 相位机

```
DOWN ──插盾 0.35s──▶ PLANTING ──▶ PLANTED ──保持 2.4s──▶ LOWERING ──解除 0.55s──▶ DOWN
```

| 相位 | 性质 |
|---|---|
| `PLANTING` | 蹲下插盾的过程，**这期间还没有格挡** |
| `PLANTED` | **不移动、不攻击**，只以 `shield_planted_turn_speed`（60°/s）转向；**正面 130° 扇区的子弹减伤 85%**；盾面转成"立在地上的墙"+ 身体下蹲 |
| `LOWERING` | **既不格挡也不攻击 —— 这就是反击窗口**（用户要的"解除需要时间"） |

三条规则合起来的效果：**插盾 = 它选择防守，代价是这几秒打不到你；而它转向慢，慢走甩不掉、疾跑弧线能甩掉** —— 于是插盾逼你动起来，而不是逼你站桩。

### 11.2 手雷成为正解（用户的设计意图）

伤害入口按**有没有方向**分成两条路：

- `take_damage_at(amount, hit_position, headshot)` —— **子弹**。用命中点算夹角，落在正面扇区内才被削减，**绕到侧后就打得动**。
- `take_damage(amount)` —— **爆炸**（手雷 / 震地脉冲）。没有方向，**正面格挡对它无效**：插在地上的盾挡不住从脚底上来的爆炸。这正好让手雷有了明确用途。

**共鸣是唯一例外**：它是"能迎上去挡的能量波"，由 `on_resonance_incoming` 预置一个 **0.25 秒时效**的格挡窗口（用时效而不是裸 bool —— 裸 bool 会被中间插入的爆炸消费掉，表现就是"手雷莫名其妙被盾挡了"）。

> 附带修掉一个**耦合地雷**：`resonance.gd` 原先用 `has_method("take_damage_at")` 判 Boss，而近战现在也实现了这个方法 → 全体近战会被误判成 Boss、连即死保底都不再生效。已改为只认 `boss` 分组。这正是"客户端猜测式判定"的典型代价。

### 11.3 参数

| 键 | 值 |
|---|---|
| `shield_plant_seconds` / `shield_lower_seconds` | 0.35 / 0.55 |
| `shield_hold_seconds` | 2.4 |
| `shield_raise_chance` / `shield_raise_cooldown` | 0.35 / 4.0 |
| `shield_block_arc_degrees` / `shield_damage_reduction` | 130° / 0.85 |
| `shield_planted_turn_speed` | 60°/s |
| `shield_planted_pitch_degrees` / `shield_crouch` | -75° / -0.14（纯姿态，可调） |

轻型死/重型不死；重型仍吃基础伤害；**共鸣必进起手相位**；起手期间算"忙"；**起手→防御→解除→普通**四相位逐个推进；**正面子弹削减、侧后不削减、爆炸绕过格挡、共鸣被格挡**；**解除期间不格挡**；激怒叠层与封顶、非重型不涨。

### 13.1 ①② 其实是同一个根因：**场上清空就结算**，而机制验证必然会清空场上

`combat_lab._on_enemy_gone()`：当 `_loop_mode` 既不是 REPLACE 也不是 WAVE、且
`_live_enemies.is_empty()` 时立刻 `_finish_round(true)` —— **打死最后一只就出结算**。

机制验证组只有 1~3 只，而且验证手段本身就是杀伤：一次共鸣（520 基础伤害）或一颗手雷
就能把场上清空。于是"按下 → 怪死光 → 结算画面"三帧连在一起，**根本来不及观察**。

→ 机制验证组自带**循环模式 REPLACE（死一只立即补同种）**：在 `GROUP_PRESETS` 里声明
`"loop": LoopMode.REPLACE`，`deploy_group()` 投放前自动切换。验证对象因此一直在场，
可以反复触发同一事件做对照。其它预设不受影响（单轮清场仍是实验场的默认行为）。

> 这属于**测试工具本身的可用性缺陷**，不是游戏逻辑错 —— 但它的代价和 bug 一样：
> 机制做了、看不出来，等于没做。

### 13.2 ③ 盾卫朝向：**符号写反了 180°**

`_face_target_while_planted()` 里写的是 `atan2(to_target.x, to_target.z)`，
而本模型 **-Z 为正面**，正确约定是 `atan2(-x, -z)`（`_face_flat_direction` 用的就是它）。
差 180° 的后果不是"不转"，而是**越追越偏、看起来在原地转圈**。

顺带补上第二个隐患：插盾期间不跑 `_update_behavior`，**目标不会被刷新**，
所以它会一直朝着"插盾那一刻"记下的旧方位。现在插盾期间按 `RETARGET_INTERVAL`
自己重新取一次目标。

## 第 15 轮：震地推不开 + 共鸣反应慢一步（已落地，待试玩）

用户实测两条：① 「震地现在机制是不是有问题，怎么**每次释放，盾卫都会被拉近一点而不是推远**」；
② 「共鸣爆发时，盾卫好像是**被打了才下盾**，共鸣爆发这个技能没有通知机制？」

### 15.1 震地推不动：击退写在了一个"贴脸时不会跑"的分支里

`melee_enemy._physics_process` 的主干是：

```
_steering.tick(...) ? → attack_cooldown / update_feedback   ← 敌人"已到位"时走这条
                    : → _update_behavior(delta)             ← 击退写在里面
```

而**击退原来写在 `_update_behavior` 里**。敌人一旦贴到玩家身上，`_steering.tick()` 就返回 true，
`_update_behavior` 整段不执行 → **贴脸的敌人永远推不动**。插盾姿态更早：它把 `velocity` 清零后
直接 return，连"看起来被推了一下"都没有。

> **贴脸恰恰是 Q 唯一的用途。** 所以这个 bug 等于让 Q 在它最该生效的场景里完全失效。

→ 把击退提到 `_physics_process` **最前面**（在 AI 与插盾姿态之前），并删掉 `_update_behavior` 里的旧副本。
原则：**击退是外部强加的运动，优先级高于 AI 决策，也高于自身姿态**。

### 15.2 共鸣反应"慢一步"：通知有，但姿态插值把它推迟了 0.35 秒

通知机制**是有的** —— `resonance._apply_burst_damage()` 在结算伤害**之前**调
`on_resonance_incoming()`，格挡也确实按这一发结算（`_brace_resonance_time`）。

问题在**视觉**：姿态是由相位机按 `delta` 插值的（`_advance_shield_state` → `_apply_shield_pose(delta*7)`），
插成"插盾"的样子要约 0.35 秒；而爆发的视觉是同一帧。两者错位，玩家看到的就是
"先被炸、盾才抬起来"——读起来就是"被打了一下才有反应"。

→ `on_resonance_incoming()` 改为**反射式**：跳过插盾起手，直接立在防御相位并 `_apply_shield_pose(1.0)` 瞬间到位。
**格挡既然这一发就生效，姿态也必须在同一帧到位，它们才是同一件事。**
概率触发的路径仍保留 0.35 秒起手（"选择防守"是有代价的）。

### 15.3 守卫

`test_heavy_response.gd` 新增两组断言：

- **击退**：构造最坏情况（盾卫处于**插盾姿态**且**紧贴玩家**）后 `apply_push(away, 30)`，
  要求 24 帧后位移 > 0.5 米，且方向与"背离玩家"一致（点积 > 0.7）。这条在修复前必然失败。
- **反射式格挡**：`on_resonance_incoming()` 之后**不等待任何帧**，状态必须已经是 PLANTED。

### 15.4 排查中被咬的两次（都记下来）

1. **`paused=true` 让物理静默不跑**：GameFlow 进场景时会暂停 SceneTree，而**暂停不阻止
   协程的 `await` 恢复** —— 测试看着在跑，节点的 `_physics_process` 一次都没执行。
   表现是"位移 0.00 米"这种误导性失败。定位靠 `can_process=false` / `paused=true`。

2. **被回收的对象**：测试世界没有地板，盾卫坠落 → `_kill_if_below_world()` 回收 →
   再读 `global_position` 直接抛错 → 协程中断、`quit()` 收不到 → **进程挂住不返回**
   （用户之前也遇到过"截图卡住不返回"，同一类）。→ 关重力、放大 `_fall_kill_depth`，

### 16.1 ① 真凶不是"推不动"，而是 `parry()` 在把敌人**拉向**玩家

上一轮我把击退提到 `_physics_process` 最前（那一步本身是对的），但用户实测仍然推不开 —— 于是写了**真实场景复现**（`tests/test_shockwave_push.gd`：在空间测试台里生成真盾卫、走真实 `Shockwave.perform`、逐帧量距离）。第一次就复现了：

```
命中=1 击退时长=0.63 击退速度=(0, 0, +10.5)   距离前=2.00
f=0..4 距离 1.82 → 1.66 → 1.50 → 1.36 → 1.23   ← 一路贴近
```

**`_stagger_velocity` 指向玩家。** 根因在 `melee_enemy.parry()`：

```gdscript
_stagger_time = _stagger_duration * 1.5
_stagger_velocity = -global_transform.basis.z * 7.5   # ← 这里
```

`Shockwave.perform()` 的顺序是 `apply_radial_damage()`（正确外推）→ `_parry_and_intercept()`（对范围内敌人调 `parry()`）。而 `-global_transform.basis.z` 是**模型面朝的方向**（本模型 -Z 为正面）—— 敌人面朝玩家，所以"破招后仰"实际是**朝玩家扑**，并且因为它硬直更长（×1.5）、执行更晚，把脉冲给的外推**整个覆盖**。

顺带一个隐藏错误：`basis` 带节点缩放（盾卫 scale 1.4），所以 `7.5` 实际是 **10.5** —— 数值和方向都不是原意。

→ 两处 `parry()`（近战 / 远程）统一改成：
- 方向 = **背向目标**（拿不到目标才退回模型背面），并**归一化**；
- **已有推力就不覆盖** —— 破招只负责"硬直更长 + 受击表现"，不该用自己的短推力盖掉脉冲的推力。

修复后同一复现：`击退速度=(0,0,-21.87)`，**距离 2.00 米 → 9.24 米**。

> 教训：**"我修过了但还是不对"时，不要再对着同一个函数加码，要写真实场景复现。**
> 隔离测试（空世界里直接 `apply_push`）一直是绿的，因为它绕过了 `parry()` 这条真链。
