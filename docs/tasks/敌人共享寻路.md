# 敌人共享寻路

## 目标与最新反馈

用户 2026-10-11 提出：**「共享肯定值得，问题只在于如何实现。比如动物吧，基本上一大群动物往哪里走或者飞，就看几个领头的，并不是每只动物都独立寻路。」** 随后用户批准复刻测试台：「可以复刻一个测试台，测试新的思路」，并确认本轮**只做计量台、不写新算法**。

用户同时提出一个待回答的判断：「上次我主要是规定了不依赖地图，换地图不需要任何针对性设置。现在看来，不针对地图进行预处理，很难做到很低的开销？」

本轮范围（用户选择）：只做计量台，把寻路开销拆成可比较的分项，用数字决定先动哪一层。不实现共享走廊、不实现领头、不实现地图预处理。

## 已核对的现状

**每个敌人完全独立寻路**，路线层面没有任何复用：

真正共享的只有：烘焙导航网格（[navigation_region.gd:50-78](../../scripts/navigation_region.gd)，参数在 [game_config.json](../../data/game_config.json) `navigation` 段全局唯一、无 per-arena 配置）、`_jobs` 的每帧预算轮转、`_admit_plan()` 的每帧配额，以及按目标共享的环锚点状态（默认关闭）。

导航实现不识别地图：`scripts/` 下八个导航文件里没有任何 arena id 或地图名分支（命中全在 terrain / 视觉 / 小地图 / 刷怪 / 菜单代码里）。

## 接口分层（决定共享边界的既有事实）

- **网格拓扑可共享**：全体敌人共用一张运行时烘焙网格，`NavigationAgent3D.radius` 只影响局部避让、不改变通道宽度（[navigation_region.gd:62](../../scripts/navigation_region.gd)）。
- **身体通行验证不可共享**：`ground_segment` / `full_support` / `safe_drop` 全按各自身体判定。
- **接战终局不可共享**：近战 40 个站位候选依赖各自落脚高度并按各自距离排序（[spatial_route_planner.gd:43-59](../../scripts/spatial_route_planner.gd)）。

## 关键判断：预处理省不掉最大的一块

开销性质分两半，与地图无关性与否无关：

| 成本 | 依赖 | 地图预处理能否省 |
|---|---|---|
| 搜索（`query_path` 的 A* 展开） | 地图多边形数与路径长度 | 能 |
| 验证（沿整条路径逐段 `ground_segment` 全身扫掠与终检） | 敌人身体与路径长度 | 不能 |

所以「不做地图预处理就难以低开销」这个判断在当前实现上不成立：搜索本来就是小头。用户上次规定的「不依赖地图、换地图不需要针对性设置」**禁止的是针对某张图人工特调**（写死坐标、按障碍名判断、给某张图单独调参），不禁止**从地图几何自动派生**。项目已经在做后者两处：运行时烘焙导航网格本身，以及按指纹校验、来源变化自动回退现场生成的 [valley_static_cache.gd](../../scripts/valley_static_cache.gd)。

## 复核：环带 / 粗略目标覆盖未生效（I-082）与预算覆盖面（I-083）

并行审查提出两条判断，本轮逐条核对（只读，未改代码）：

### 1. `goal_override` 从未生效 —— 成立，运行数据一致

- 代码路径：[spatial_route_planner.gd](../../scripts/spatial_route_planner.gd) 的 `begin()` 先按 `target` 算出 `goal` 与 `_goal_support`，之后才读 `has_goal_override`；[combat_spatial_controller.gd:239-244](../../scripts/combat_spatial_controller.gd) 是**先调 `begin()`、后设置** `goal_override` / `has_goal_override`。
- 运行证据：三次独立运行的探针 `goal_check` 完全一致 —— `requested=(12.0, 0.06, 6.0)`、`actual=(0.0, 1.045, 6.0)`、`error_xz=12.0`、`override_flag=true`。`actual` 正是目标的支撑点。三次分别是 `--ui=0 --ring=0` ×2 与 `--ring=1` ×1。
- **影响面比「界面记录与实际搜索不一致」更大**：`_pursuit_goal()` 只在 `band > 0` 时走非精确分支，所以受影响范围恰好是环带目标与粗略目标这两个功能——它们的**搜索目标整体没有生效**。两者默认关闭，因此生产默认口径的分桶测量不受影响。
- 由此需要重新审视的既有结论：I-075 / I-077（同心环目标在接战链相位变差、环带计划失败多于精确目标）与 I-074（LOD 启用后停在 `checking`）都是在这个前提下定位的，当时实际生效的只有环带簿记、过期判据、降频与 live-aim 门；「环带目标本身好不好」尚未被有效检验。I-074 对 `_publish_route` 过期判据的修复是独立的，仍然成立。

### 2. 2.2 ms 预算的覆盖面 —— 成立

- **预算内**：`process_jobs()` 循环里的 `job.advance()` 与 `owner._publish_route()`。
- **预算外**：`tick` → `_request_route()`（`_pursuit_goal` → `_choose_band_goal` → 最多 3 次 `_direct_walk_proof`，每次都做一整段 `ground_segment`；`_coarse_point` → `map_get_path` + `floor_at`；`_planner` → `begin()` 的 `Query.support(target)` 与 `set_attack_goal` 的 40 个候选）、`tick` 内的 `escape_plan` 与 `_walking`、`gate_motion` / `_move_override`。
- 补充一点：同一份开销**跨预算边界** —— `escape_plan` / `_walking` 既从 `tick`（预算外）调用，也经 `_route_landing_allowed` 从 `advance`（预算内）调用。
- 且 `advance` 的 deadline 只是「开始下一步」的门：实测 `job_us_p95` 24.4 ms、`walk_route` 单次最大 86.7 ms，均远超 2.2 ms。
- 结论：`last_job_usec` 不能当作规划总开销，「整帧 − `last_job_usec`」不能归因于角色移动或物理。这条不影响本轮分桶（分桶逐函数计时，预算外的 `ground_segment` 一样记进 validation 桶），两者可互相校验。

两条均已按登记规则写入 [问题台账](../issues.md)：I-082 补上运行复核结果，预算覆盖面新登记为 I-083。

### 3. 修复 I-082 与修复后暴露的问题（本轮已改代码）

用户 2026-10-11 指示「修 I-082」。改动只有一处顺序，加一处契约说明：

- [combat_spatial_controller.gd](../../scripts/combat_spatial_controller.gd) `_planner()`：把 `goal_override` / `has_goal_override` 的设置移到 `job.begin()` **之前**；`set_attack_goal()` 保持在 `begin()` 之后，因为它依赖 `begin()` 设好的 `body` / `target`。
- [spatial_route_planner.gd](../../scripts/spatial_route_planner.gd) 的 `goal_override` 声明处写明「只在 `begin()` 内被读取，必须在 `begin()` 之前设置」的顺序契约，避免再次静默失效。

**验证（修复生效）**：探针 `goal_check` 由 `error_xz=12.0`（`actual` 是玩家支撑点）变为 **`error_xz=0.0`**（`actual == requested`）。证据 `_artifacts/godot-ruin_star_new/nav_goal_fix/20261011_222926_c4db0ed6/reports/navigation_cost_audit.json`。

**默认路径无回归**：`test_navigation_main_scene` / `test_navigation_obstacles` / `test_navigation_moving_target` / `test_nav_path_shape` / `test_nav_shape_fallback` / `test_navigation_live_aim` 全部通过。这是因为 `ring_goal_enabled` 与 `coarse_goal_enabled` 默认关闭时 `_goal_band()` 返回 0，走的是精确分支，本轮改动不触及。证据 `_artifacts/godot-ruin_star_new/nav_i082_default/20261011_223003_99eff2fe/reports/summary.md`。

**修复暴露的真正问题（新登记 I-084）**：覆盖生效后环带组两项测试失败。**先更正上一版本的归因**：本记录初稿写成「到达环带目标后不再触发重画」，那是误读——`replans` 字段是 `NavSteering.path_requests`（agent 设目标次数），它塌到 11~39 是「`tick` 早退、没走到运动路径」的**下游症状**，不是机制。同样，「环带模型本身明显有害」是错误归因：几何上到更近的点不可能更难，可复核的只是**当前环带目标选点与推进策略**的表现。

实测事实：

| 相位 | 在追个体 | 最长连续零速 | 零速比例 | 结束时 `relocate` 数 |
|---|---:|---:|---:|---:|
| 接战链对照（环关） | 24 | 86 | 0.045 | 0 |
| 接战链·弹开（环开） | **14** | **702** | **0.433** | **10** |
| 接战链·平滑（环开） | **13** | **865** | **0.551** | **9** |

关键在于带档位规划的成败：`ring_used` 274~298 次中 `band_fallbacks` 178~217 次产出空路线，**失败率 60~75%**；对照（精确目标）相位几乎为 0。所以主因指向**环带候选点本身常常得不到任何可行路线**，而不是「环带比点难走」。

这里有一处与直觉模型的差异必须点明：实现里的档位目标**不是「环上离自己最近的点」**。[nav_ring_anchors.gd](../../scripts/nav_ring_anchors.gd) 的 `region_goal()` 是从**目标走过的轨迹**里挑一个落在该环带内的点（按「离追击者近 + 靠近环带中线」评分），没有合格轨迹点时才回退到环圆心。也就是说目标是**目标曾经站过的位置**——那是玩家的身体能到的地方，不保证这个敌人的身体能到。另外单环配置不可用：`configured()` 要求 `radii.size() >= 2`，只有一个环时模型直接返回空、走精确目标。

环带与 LOD 仍默认关闭，生产默认配置不受影响。证据 `_artifacts/godot-ruin_star_new/nav_i082_ring/20261011_223153_1cd542ae/reports/`。

### 三个直接结论

1. **身体验证是最大的一块（约 46–48%）**，全部是本项目自己的物理查询：`floor_at` 6.88 s（913,272 次）、`support` 6.30 s（501,583 次）、`motion_clear` 2.59 s、`ground_segment` 1.91 s、`ground_pose` 1.69 s。与地图无关，**地图预处理省不掉**。
2. **`search` 桶其实不是路径搜索**：A* 的 `native.query_path` 全程只有 847 次、0.25 s；这一桶绝大部分是 `native.closest_point` 63,127 次共 5.14 s（约 81 µs/次）与 `closest_owner` 16,167 次共 1.65 s。真正贵的是**导航投影**，而且同一个目标与落脚点的投影被 256 个个体各自重算——这是最容易共享的一块，且它同样与地图无关。
3. **APS 形状流水线几乎免费（0.3–0.4%，合计 0.17 s）**。此前对形状流水线性能的担心在本口径下不成立。

另注：该口径下全体零速比例 0.486 / 0.492、活跃个体 131 / 129，与 I-066 登记的现象一致；分桶只统计成本，不判定追击表现。

### 口径偏差

注入计时给每个被计时调用加一对 enter/leave，绝对耗时被抬高（帧 p50 约 59–61 ms、p95 约 84.5 ms，**不是帧率结论**；无注入口径见 I-064）。最高频的三个纯叶子函数（`_floor_ray` / `dimensions` / `parts`）已改为只计次、其耗时由父函数吸收。同配置两次运行的绝对总量差约 5%（40.46 s / 42.48 s），分桶占比稳定；绝对数字需多次运行取分布，不能单次引用。
