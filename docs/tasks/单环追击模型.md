## 正式导航瓶颈计量（2026-10-12）

本轮用户问「正式场景里的瓶颈在哪里？」本轮仅分析与计量，未修改正式运行代码，也未对地图做特例调整。结论：正式导航主要消耗在整条路线的地面与身体通行验证；同步重步骤突破规划预算，排队后移动目标又使大量已算出的路线过期，形成反复规划与停等。原生路径搜索不是当前主要耗时。

**范围与证据**：256 体、全区域投放、持续移动目标、900 物理帧、预热 120 帧、种子 64768、环模型关闭、UI 关闭，Godot 4.7.2。使用 `navigation_test_actor.gd` 的正式默认空间控制器与 Walk 身体配置，加载正式地图几何。它覆盖正式导航链路，不等于完整近战敌人的战斗、动画与渲染负载。隔离副本分为无计时注入、粗分项、细分项三次运行；函数计时包装会增加耗时并改变任务推进时序，分项只用于判断主次，不与无注入帧耗时直接相加。[分析报告](../../../_artifacts/godot-ruin_star_new/formal_nav_hotspots/20261012_075207_3d9920a0/reports/bottleneck_analysis.md)、[无注入数据](../../../_artifacts/godot-ruin_star_new/formal_nav_hotspots/20261012_075207_3d9920a0/reports/raw/navigation_cost_audit.json)、[细分项数据](../../../_artifacts/godot-ruin_star_new/formal_nav_hotspots/20261012_075207_3d9920a0/reports/detail/navigation_cost_audit.json)。

无注入帧间耗时 p50 37.356 ms、p95 50.489 ms、平均 38.568 ms。规划推进每帧平均 9.455 ms、p95 18.132 ms、最大 60.993 ms；780 个测量帧全部超过配置 2.2 ms。末帧队列 244 个，状态 checking 244 / approach 12，106 个尚未到达的个体已连续近零位移超过 2 秒。诊断正常退出只说明脚本可运行，不能作为性能或追击通过结论。

细分项以包装函数的独占耗时归组，避免把调用者与子函数重复相加；总计 41.944 ms/帧，其占比只对应这一次有注入运行：

| 项目 | 独占耗时 / 帧 | 占比 | 含义 |
|---|---:|---:|---|
| 地面、支撑、身体通行验证 | 19.029 ms | 45.37% | support / floor_at / ground_segment / motion_clear / ground_pose / full_support 等 |
| 实际身体移动与跨坎 | 7.681 ms | 18.31% | Ground.move / step_landing |
| 控制器与规划器剩余工作 | 7.370 ms | 17.57% | 包括未单独包装的内部调用，不能全称为决策计算 |
| 原生导航最近点投影 | 5.356 ms | 12.77% | 仍有约 66 次/帧原生查询 |
| 测量体自身 | 1.231 ms | 2.94% | 调度与统计等剩余工作 |
| 方向跟随剩余工作 | 0.850 ms | 2.03% | 包含未单独包装的跟随内部调用 |
| 原生路径搜索 | 0.265 ms | 0.63% | 约 1.11 次/帧，不包括投影与身体验证 |
| 路径形状处理自身 | 0.163 ms | 0.39% | 不包括形状处理调用的物理验证与投影，它们已归入上列 |

细分项每帧约 1339 条地面射线、312 次身体运动检查。`ground_segment` 沿整段以 0.45 m 采样，精细复核为 0.15 m；每点查地面、法线/落差、身体运动，受阻时再尝试跨坎。100 m 普通段约需 223 个采样位置。不是每个位置都做 49 条射线；49 射线是独立的完整落脚支撑检查。规划前直接通行试探、路径点落到物理地面、路线分段验证、形状处理后的验证，以及追击每帧的支撑/运动闸门叠加，造成这一大项。身体尺寸已有逐帧缓存，不能将其作为新的优化点。

**移动目标的重复劳动已复核**：[额外结果计数](../../../_artifacts/godot-ruin_star_new/formal_nav_publish_outcome/20261012_080844_37cee069/reports/coarse/navigation_cost_audit.json) 在隔离副本中进一步区分目标过期时 `job.result` 是否非空。780 个测量帧内共 830 次普通规划发布处理：102 次接收非空路线、4 次接收空结果、702 次拒绝已有非空路线、22 次拒绝空结果。即 804 个非空结果中 702 个（87.31%）因目标已移动过阈值而被拒绝；过期结果中 96.96% 已有非空路线。这里是结果数量比例，不是 CPU 时间浪费比例；非空也不保证当前身体位置和几何条件仍允许整条路线直接使用。

代码对应：`combat_spatial_controller.gd::_publish_route` 对普通精确目标，以目标当前位置相对 `_goal_sample` 超过 `_replan_distance()*2` 拒绝发布，并令计时器归零。`process_jobs` 和规划器 `advance` 只在步骤间检查期限，`walk_route` 内整段验证无法暂停，因而 2.2 ms 预算不能约束单个重步骤；`tick` 的支撑、开工、运动闸门还存在预算外工作。队列、过期与重做的数据和这条代码链一致，但本轮没有逐一证明每个长期停顿个体的完整因果链。现象登记 I-092；既有预算问题 I-064 / I-083、正式 256 体停顿 I-088 保留待修。

**上一轮两项优化为何在正式链路收益小**：正式链路粗/细计量中 `direction_to` 仅约 24 / 22 次/帧，另外大量个体由空间控制器覆盖移动或停在 checking，远少于直接 Agent 观察台的 256 次/帧。本轮跨坎预验已降到约 2–4 次/帧，不再是大头。剩余投影还来自 `needs_route`、路线规划、路径形状验证等未接共享缓存的入口。不能直接扩大最近点缓存容差，I-089 已有跨面误差反例。正式精确模式 `_tick_stride` 直接返回 1，远距离规划降频仍与已关闭的环模型开关绑定；无注入 full_ticks 230083 / cheap_ticks 0。跳跃、攀爬、破障执行期间暂停追击规划已有实现，不是缺失项。

**优化方向，仅建议，未开始实施**：优先让移动目标下已验证的路线前段可安全复用，按当前身体位置、导航版本与目标变化连接/刷新末段，减少整条路线重做与同帧重复支撑查询；同时把重验证拆成可暂停步骤，预算覆盖开工与跟随验证，配合队列优先级。只拆分会延长排队、增加过期，不能单独作为解决方案；也不能直接删除过期保护。再将远近调度从环目标解耦，保留精确目标但降低远处重复验证频率；最后审查剩余原生投影的相同输入/安全几何复用，不牺牲跨面正确性。这些优化应与地图无关，仍用多体全区域和移动目标验证。

本轮未验证：完整正式场景的 GPU/动画/攻击耗时、真实近战攻击姿态最多 5×8 个候选的附加成本、更多种子与长时间稳定性、I-089 / I-091 的修复。两份运行源码 SHA256 均与当前项目对应九份运行脚本一致；诊断注入只留在项目外隔离副本，临时驱动与副本保留为诊断归档。导入及四次诊断均正常退出，无脚本/资源错误；这不是行为验收。交付前 `python -B tools/project_hygiene.py check` 退出码 0：根目录整洁、产物路径规范、文档链接有效。本轮分析完成，建议尚未实施。

## 目标与最新反馈

以下为单环方向退役前的定义及过程记录，不作为当前运行规则。

用户 2026-10-11 连续三轮收窄需求，最终定义：

1. 「归零，重新建模型，同样的地图，一个环，直径60，追击者的目标是距离自己最近的环上的点。」
2. 「主角移动会带着这个环一起走。」
3. 「什么调节参数都不要了，我们从新搞。」
4. **「进圈就kill，重新在圈外生成一个新的，我只看敌人追圈。」**

因此最终模型只有一条规则，**不需要战斗链路，也不需要「进圈转精确追击」**：环心＝主角、半径固定 30 m；追击者在圈外走向**环上离自己最近的点**；一旦进圈就销毁并在圈外重新生成一个。

环心跟随主角这一条把旧模型的状态全部消掉：没有锚点、没有拖动、没有传导、没有解耦，也没有跨环迟滞——I-085 登记的三处自相矛盾（类头说链条传导 / 循环注释说只看目标 / 形参叫 `inner` 却传 `target`）在新模型里不存在。

## 第八轮：A 项的两种读法都做了——一条拒绝、一条只省 0.34 ms（2026-10-12）

用户选「做 a」（原计划：`full_support` 那约 1.5 ms）。查实现后结论要改。

### `full_support` 这一条**拒绝做**

`spatial_query.full_support`（168 µs/次）实际是 [jump_landing.gd](../../scripts/jump_landing.gd) 的 **49 条射线**：32 个圆周点 + 约 16 个脚印内部网格点 + 中心，采样步长 0.25 米。内部网格点专门用来抓「脚印中间有洞」，圆周点抓「站在棱边」——两者都对应真实失败模式。要省时间只能减少采样，那是**放松支撑检查**，与上一轮射线改高度属于同一类错误。**不做。**

### 改做的那一条：环上候选的投影接入共享缓存

发现 `nav_ring_goal._standable()` 的投影是**直接调原生**、没走缓存（约 98 µs/次 × 19 次/帧）。改成 `ProjCache.closest()` —— 同一个纯函数、同一个容差，steering 层已经在用。

结果分两层：

| 口径 | 前 | 后 |
|---|---:|---:|
| `_refresh_goal` 每调用独占（机制层） | 112 µs | **94 µs** |
| 帧 p50（端到端，256 体 / 600 帧） | 34.85 ms | 34.90 ms |

**机制层省了 18 µs/次 × 19 次/帧 ≈ 0.34 ms/帧，端到端量不出来（在 5% 运行波动内）。**

### 为什么只省这么多——一条可推广的结论

投影缓存**只在同一个位置被高频重复查询时才划算**：

- steering 的脚下投影：每帧都查、每帧只移动 0.067 米 → **命中率 81.8%**（缓存那一轮的主要收益）。
- 环上候选点：每 15 帧才查一次，其间位置移动约 1 米 → **几乎必然未命中**，缓存帮不上。

同理，之前设想的「候选没明显移动就复用支撑结论」也不成立：候选每 15 帧就移动约 1 米。

### 修正后的总账

**剩余空间 ≈ 0，缓存那一轮（79 → 34.6 ms）就是全部大头。** 34.9 ms 的构成：物理地板 ≈14.1 ms、引擎侧每帧跟随 ≈10 ms、身体验证 ≈4.7 ms（不能放松）、观察台自身 ≈4.0 ms。

唯一还能明确拿到的是**观察台自己的取舍**：目标重算从 15 帧放宽到 30 帧，验证次数减半、省约 2.3 ms，代价是目标滞后 0.5 秒。这是台子的调整，不是正式游戏的优化。

证据：机制层 `_artifacts/godot-ruin_star_new/ring_cost_after/20261012_001651_22970ab9/reports/nav_cost_buckets.md`；端到端 `.../ring_after_a/20261012_001757_a0915cce/`。

## 第七轮：脚下高度改射线的实验——**失败并回退**（2026-10-12）

**结论：不要这么做。** 记在这里是为了防止以后有人再试一遍。

动机：`direction_to()` 每体每帧的 `ProjCache.closest(nav_map, feet)` 结果只用于取 Y，而原生导航投影实测约 98 µs/次、向下射线只要 1~2 µs，看起来是笔稳赚的账。

做法：脚下高度优先用向下射线（起点抬 0.6 米、下探 1.6 米、只接受可走法线），取不到才退回导航投影。

实测（256 体 / 600 帧 / 同种子 / 缓存都开）：

| | 导航投影（原样） | 向下射线 |
|---|---:|---:|
| 帧 p50 | 35.03 ms | 39.75 ms |
| 进圈 | 380 | 307 |
| 掉队回收 | 56 | **279** |
| 窗口零速比例 | 0.000 | **0.159** |
| 停滞原因 | 1 次 | `blocked_or_sliding` **563** + `unreachable` 38 |
| 偏转次数 | 93 | 4919 |

**原因**：导航起点的高度必须与**路径点同处一个面**，而路径点落在**导航网格**上。导航网格是体素烘焙的，平地上就可能比真实碰撞面高出两个垂直栅格（≈0.5 米，`spatial_route_planner.gd` 里本来就记着这件事）。射线取的是真实碰撞面高度，等于把起点和路径点错开半米，第一个路径点永远够不到——所以停滞、掉队、偏转全部爆炸，帧耗时反而更高。

**已回退**：`nav_steering.gd` 恢复用导航投影，并在该处写明这段结论；探针的 `--ground-ray` 开关一并删除。回退后复测 p50 34.85 ms、掉队 57、256/256 在追、零速 0.001（`ground_ray_revert/20261012_001321_8200660e`）。

### 修正后的剩余优化空间

原先估的「三项共省 ≈11 ms」作废。按第七轮的实测份额重新算：

| 项 | 每帧 | 能不能省 |
|---|---:|---|
| `physics_move`（`move_and_slide` + `step_landing`） | ≈14.1 ms | **地板**，不改移动方案砍不掉 |
| `direction_to` 里缓存未命中的原生投影（≈47 次/帧 × 98 µs） | ≈4.6 ms | 只能靠放宽容差，但那会重犯第七轮同类错误（高度必须贴导航面） |
| `direction_to` 的 GDScript 与 NavigationAgent 调用 | ≈10 ms | 引擎侧跟随，难在不改跟随方式的前提下压 |
| `spatial_query.full_support`（168 µs/次 × ≈19 次/帧） | ≈3.2 ms | 可在候选未明显移动时跳过，预计省一半 ≈1.5 ms |
| 观察台自身（`bench_ring`） | ≈4.0 ms | 只是台子开销，不属正式游戏 |

**实际可再省约 1.5~2 ms：34.85 → ≈33 ms（≈30 FPS）。** 投影共享缓存（79 → 34.6 ms）是这一轮真正的收益，后面是长尾。

另外修正一处早先的说法：I-070（`PathStyle.settings()` 每次 `duplicate()`）在 `direction_to` 里**只在 `_timer <= 0.0` 时被求值**，约 19 次/帧，成本 ≤0.05 ms/帧，可忽略——它是个正确性味道，不是性能项。

要达到 60 FPS（16.7 ms）只有两条路：**减少个体数**，或**换移动/物理方案**（远距离个体降频物理、非物理位移等），都超出调参范围。

## 未解决：256 体的帧耗时

同一口径下无渲染帧耗时 **p50 69.1 ms / p95 75.5 ms**（约 14 FPS），这与项目既有的 I-064 同一量级（旧压力测量 256 体 P95 42.8 ms，但那是纯移动测量体，没有本台每帧的选点）。本轮**没有做性能优化**，也没有把帧耗时拆开。

## 第三轮：观察台的三处实现错误（2026-10-11）

用户跑观察台反馈「经常有追着追着就停了……也没有红色高杆」「场上居然没了，刷新机制也有问题吧」。三个都是我的实现错误，互相叠加：

1. **追击者没有可见模型**。`_make_actor()` 只加了碰撞胶囊，没加任何 Mesh —— 之前看到的"在动的东西"其实是轨迹线和目标标记，不是敌人本体。
2. **竖直标记在正俯视下不可见**。相机是正交正俯视，而红杆与橙色竖标都画成竖直方向；竖直的线从上往下投影**只是一个点**。所以停滞红杆虽然一直在画，画面上却看不到。现在所有标记改成**水平十字/圆环**。
3. **重生把地面点当成身体原点**。`place_at()` 收到的是地面高度，而胶囊中心才是原点，于是每个重生的追击者都**半埋进地里**——这正是「停了」的来源。现在按 `half_height + 0.05` 抬升。

另外修了两项规则性问题：

- **停滞判据换成窗口净位移**（0.6 秒窗口、0.25 米，与正式 NavSteering 的脱困判据一致）。原用逐帧位移 < 0.002 米，贴墙抖动的人逐帧都在动却站着不动，这正是计数器一直显示 0、红杆不出现的原因。实测两个口径差两个数量级：**逐帧 0.001 / 窗口 0.077**。

## 两条硬规则（用户 2026-10-11 明确）

### 这份结果能证明到什么程度

1. **追圈行为已被实际行使，但不等于全区域验证。** 投放期望半径仅 32–48 m（投影后位置可能漂移），且 `_connected_to_ring()` 用一条到环心的完整路径筛掉不连通位置；超过环心 60 m 就回收。不是预先固定地图坐标，筛选规则本身通用，但它排除了最容易长期失路的样本。停滞窗口从 50 降到 2 的同时改变了投放样本，不能全归功于脱困能力提升。
2. **进圈不是完整路径到达率。** 进圈判定实际为水平距离 ≤31.5 m，绘制环仍为 30 m；环随标记移动，也可能主动扫过个体。381 次进圈与 57 次掉队回收是事件数，不能计算为每个体成功率。57 次占已记录两类回收事件约 13.0%，不能当作导航失败率。环心正常速度 12 m/s、冲刺 20.4 m/s，追击者 4 m/s；直线远离后方个体时，即使个体持续正确追击也会掉队。
3. **没有检验个体之间的避让。** 追击者碰撞层为 4、碰撞掩码为 1，互不物理碰撞；`NavigationAgent3D.avoidance_enabled=false`。256 体证明的是对地形的追圈负载，不包含拥堵与互相避让的负载。
4. **选点成功不是路线成功。** `resolve=10627、fallback=0` 只说明本次候选找到可站立解析结果。它不查询路线可达性，候选角只覆盖几何最近方向的 ±40°，不保证复杂障碍下找到整个圆周中的可达入口。几何最近点也不必是路径代价最小的点。
5. **目标点验证有一个明确的接口缺口。** `landing_clear()` 原本仅检查环境层之外的角色实体；本台 `collision_mask=1` 使其直接返回 true。`full_support()` 与 `ground_pose()` 检查脚下支撑/脚印，不等价于完整身体的静态环境净空。本次未复现穿透，导航烘焙自身也有身体余量，不能据此认定它就是已观察停滞的根因。已登记 I-086。
6. **个体进圈分布目前缺失。** 探针的 `cycles` 仅按单帧位移 >5 m 推断重生，混入掉队回收且漏掉较短重生位移；最终 70 个槽位 `cycles=0`，不能推出这 70 个个体寻路失败。已登记 I-087，后续应按真实事件区分进圈和掉队，再讨论个体成功率。

### 成本解释与优化优先级（未实施）

现有说明中「每帧选点」需要区分：`_refresh_goal()` 已按 `GOAL_REFRESH_FRAMES=15` 错峰重算，常规每个体每秒约 4 次；10627 次成功解析除以 256 体 × 10 秒约 4.15 次/体/秒，含重生和停滞补算。不是 256 个体每帧完整选点。

但每个体的 `direction_to()` 仍在每个物理帧做 `map_get_closest_point_owner(position)` 和 `map_get_closest_point(feet)`，正常情况下约 512 次此类调用/帧；实际设置新目标时另做一次目标投影，并触发 agent 路径更新。环上点的支撑验证还包含物理查询，`Ground.move()` 包含角色移动和受阻后的跨坎检查。重生的 `_spawn_one()` 每候选又做地面查询与到环心的完整路径查询，最多试 60 次。报告没有各项调用次数、耗时或真实 `path_requests`，所以先前「80 µs/次、占 40–60 ms/帧」只能保留为估算，不能称为已定位的主因。

可按以下顺序推进后续工作，全部基于导航地图版本、实际位移与几何检查，不增加针对当前地图的特例：

1. **先分开计量，再决定改哪里。** 至少分为地图/脚下投影、agent 路径更新、环点支撑验证、角色物理移动与跨坎、重生连通查询。记录每帧调用数及 p50/p95/p99，分别观察平稳追击与大量回收帧，避免对包含引擎工作的整帧数字直接归因。
2. **优先消除稳定状态下的重复查询。** 地图有无有效导航面的判断可按导航版本缓存；脚下高度要结合本体地面接触或局部查询复用，遇到坡面、楼层、导航修改时正确失效。不能把所有个体简单共用同一个地面高度。环点解析和 agent 设置目标重复投影，应明确可复用的导航表面结果。
3. **避免无必要的重规划，保持每帧走旧路。** 当前每 0.25 秒取一个随环心、个体位置一起变化的精确点；`set_goal()` 的偏移 >1 m 会强制重规划，常规重规划阈值为 0.8 m。即使环心不动，个体侧向绕障也会改变「最近点」，旧路可能反复被更新。可以仅在已有终点失效、偏差超过允许范围、路线阻塞或地图版本变化时换路，并保留现有错峰机制；容差必须验证移动目标与复杂墙角，不能仅为了耗时好看而放大。
4. **隔离观察台回收本身的成本。** 同帧多次投放可共享环心导航投影；连通判定应复用按地图版本更新的可靠连通信息，或复用必要路径查询的结果，不能共享某个个体的可达结论给全体。测试规则若仍为只进圈结束，就要区分「能够到圆内任意合法区域」与目前更强的「能够到环心」筛选。

Godot 官方同样建议避免无必要的目标重置、错峰路径查询，并指出搜索成本与导航多边形及边的数量相关，不能只按直线距离衡量：[导航性能优化](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_optimizing_performance.html)。因此单环替换了目标位置，并不自动等于计算复杂度下降；当前报告尚无证据证明它已经达到降低规划成本的原始目标。

当前缓存用「同一个 0.5 m 空间格 + 两次输入距离 ≤0.3 m」判命中，返回历史投影。投影到不连通导航面时，最近面可以在边界两侧发生跳变，输入距离不能作为输出误差的上界。

建议将复用凭据升级为可验证的同一导航多边形/支撑面与有效边界范围，边缘、换层或失去支撑时回退精确查询；身高较高的目标点与脚下高度查询要区分用途。仅存 region RID 不足以覆盖 region 内多个断开的多边形。扩大格子或容差之前先处理 I-089；不能继续沿用「误差必定 ≤0.3 m」的说明。

初次独立舞台探针只等到 map iteration>0，却未等到可查询面，读到零点；第二次等待又提前调用未同步查询，均已保留原始日志。最终等待「iteration>0 且可查询面有效」后无引擎错误并复现，分析只引用最终结果。临时驱动与注入副本保留在本轮 `tmp/` 作为诊断归档，不进入正式实现或自动验收。

### 优化顺序（未实施）

1. **让跨坎预验仅在有必要时发生。** `_contact_push()` 在读取并筛选碰撞法线前就调用 `step_landing()`，本轮导致几乎每体每帧一次预验；实际 `Ground.move()` 受阻后的跨坎仍应保留。可先筛出确有不可行走表面接触、且在顶着障碍走的情况，再预验是否为可跨低坎；不能只读 `is_on_wall()` 就假定所有坡角判据等价。状态与运动一致时可评估复用同帧预验，但当前预验前探 0.1 m、实际移动约 0.067 m，姿态也可能变化，不能无条件共用。相关成本约 3.60 ms/帧，真实可节省比例要复测。
2. **地图有无导航面按地图版本共享，而非继续按位置建表。** `owner_valid()` 的调用方只使用 RID 是否有效，原生 API 是返回最近导航面的 owner，不是判断本体是否在导航面内。当前仍会在每个新位置格查询该布尔值，本轮原生调用约 21.94 次/帧、2.03 ms。可按 map RID 与 iteration 校验并保存有效面的存在性，空地图/未同步地图必须等待和重试；导航区域开关、地图重建要正确失效。`_fresh()` 本身平均约 0.47 ms/帧，可合并重复版本查询，但需保留地图同步变化的正确响应。
3. **复用已知导航表面，减少第二次投影。** `Ring._standable()` 已拿到投影与地面支撑，之后传给 agent 时又将身体中心目标投影一次。可同时保留导航表面点、身体落脚姿态与版本，把正确表面结果传给 agent；脚下高度仍必须对齐导航网格，可研究导航多边形的局部查询与有效范围。不能把别人的高度或旧 region 随意套给本体。当前位置缓存 miss 与环点候选投影应分开统计，以决定是否值得从导航网格自动生成局部查询索引；最新文件的候选投影已接共享缓存，但仍未直接复用解析出的导航表面点。第七轮用真实地面射线替代导航高度已失败并回退：物理地面与导航烘焙面有高度差，不能再作为等价替换建议。
4. **共享脚印几何与可复用的目标验证。** 相同体型的脚印边界、内部采样点和向下扫掠形状可以按尺寸、形状、缩放与朝向缓存。当前 `supported()` 每次重新生成 32 点边界与内部网格，再发多次真实射线；`ground_pose()` 每次新建形状。本轮完整脚印约 2.82 ms/帧、姿态约 0.72 ms/帧。先缓存几何，保留实际支撑查询；完整可站立结果只有在目标位置、支撑面、身体条件与物理几何版本满足复用条件时才可共享，不能把相邻点都视为同一块安全地面。I-086 的完整身体净空缺口仍需单独处理。
5. **有条件保留仍有效的路线终点。** 若允许合法环目标少量漂移，旧终点仍能进入当前圈、路线没受阻时，可以保持路线；环移动使旧终点无效、换层、导航修改或脱困时再更新。当前选点约 4 Hz、agent 新目标约 2.69 Hz/体；重规划与支撑验证的触发可拆开，先便宜判断候选或旧终点是否仍有效。这个方向涉及目标选择语义，应与原「最近点」要求核对，不能只放大阈值来掩盖目标移动。
6. **需要更大规模时再评估物理层的分级。** 256 次角色物理移动本身约 9.9 ms/帧；仅降低规划频率仍会保留每体每帧的 `move_and_slide()`。远场改用较低频的安全移动检查、近场或受阻时恢复完整物理，可能突破这一成本，但属于行为与碰撞调度的架构改动，需要验证持续移动目标、墙角、坡面、楼层与切换连续性，不能宣称无损或已经能达到 60 FPS。

以上计量不支持第八轮「剩余空间 ≈0」的结论：物理桶包含尚未按必要性筛选的跨坎预验，不能全算不可削减的移动底价；地图有效性布尔查询也不需要继续按位置格重复获取。保留 49 条真实支撑射线，与预计算不变的脚印几何并不冲突；后者的具体收益尚未计量，不能把整个支撑函数 2.82 ms 都算作可节省。上述方向都需对照复测，尚未证明能达到 60 FPS。

当前不优先：重生连通查询（本轮平均仅 0.286 ms/帧）、UI 微优化（无界面约 0.1 ms/帧）、多地图缓存（当前仅一个 map）、整表淘汰策略（本轮未触及 LIMIT）。后两项在长时间或多地图运行时再测：目前仅保存一个 `_map`，多个 map 交替会整表清空；超过 120000 条直接整表清空可能造成冷缓存集中重算，尚无当前场景触发证据。

以上建议均根据导航面、身体条件、移动与地图/物理版本自动判定，不新增当前地图的特殊坐标或障碍规则。后续验证应保留 256 个活跃追击者，增加多种子、全区域与更长运行，包含静止/持续移动/折返环心、坡面/断层/上下层，以及动态导航更新；同时核对耗时、每体进圈/掉队、停滞、支撑和缓存误差，不能只看缓存命中率。
