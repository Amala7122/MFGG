# 30 个真实敌人的完整实战性能修复（持续任务）

状态：**进行中，未通过性能/玩法验收**。不再把“探针完成”或“局部耗时下降”标成性能问题已解决。

基线：用户 i7-4790K + RTX 2080、30 只真实敌人约 25.1 FPS，禁用敌人全部 `_physics_process` 约 143.8 FPS；敌人单物理步（按兵种统计）合计约 7.2 ms。这是用户机器上的一次测量，仍须用同场景逐渲染帧的 **physics_steps** 与引擎时间线对齐。25.1 FPS 对应约39.8ms/渲染帧，但它并不证明脚本独占32.9ms，可能包含补帧和渲染更新。

## 不可破坏的交付条件

- 固定机器、图形档位、实际分辨率、关卡、场上存活敌人构成；要求玩家能正常战斗，敌人真实追击、行动、出招、受击、击退、死亡、逃出坑沿和能力跨层。
- 30 只普通敌人先达到长期稳定可玩目标：60 FPS、P95 帧时间 ≤16.67ms，记录 P99/最长帧、physics_steps 分布和敌人总数；100只真实敌人仍是长期验收目标。
- 不减少真实人口、不用禁止动作/AI/渲染换 FPS、不改变攻击队列及地面预警可用时刻；一旦攻击动作退化立即判失败。
- 所有正常玩法必须仍使用现有敌人代码；不能重复 PR #12 的“跳过通用控制器”实验。PR #11 用户无可察觉收益；PR #12 帧率只稍升、傀儡大量停在玩家周围不攻击，两者均关闭且未合并。
- 当前分支以 `codex/development-snapshot-20261021` 为基础，**CPU 审计与详细记录默认完全不启用，没有刻意改变战斗决策**。引入的是独立诊断结构，不代表 FPS 已获改善。

## 正式游玩：两种互补记录

Godot 可执行文件置于项目根目录时：

**A：看真实帧率与物理补步。** 用惯常方式进入真实战斗；实际移动、躲避、攻击，尽量包含至少一段完整30敌人的交战过程。运行前确认下面路径在项目目录之外：

```powershell
.\Godot_v4.7.2-stable_win64.exe --path . -- --perf-log --perf-detail --perf-output=D:\MFGG_Perf\normal
```

**B：定位耗时和攻击行为。** 相同场景、敌人配置和游戏操作；启用每8个物理步一次的 CPU 路径采样（此模式有额外开销，不能拿它的 FPS 当发布成绩）：

```powershell
.\Godot_v4.7.2-stable_win64.exe --path . -- --perf-log --perf-detail --perf-enemy-cpu --perf-output=D:\MFGG_Perf\cpu
```

退出游戏后各目录都有：

- `perf_play_<stamp>.csv`：旧版每0.5秒汇总格式，供兼容历史数据。
- `perf_play_<stamp>_frames.csv`：**每渲染帧**的真实墙钟时间、Godot 传入的 delta、这一渲染帧包含的实际物理步数、真实敌人数量、process/physics 监视器耗时、draw/primitives/nodes。
- B 模式还会生成 `perf_play_<stamp>_enemy_cpu.csv`：每个半秒窗口，按脚本调用入口抽样的次数、累计包含子调用耗时及单次最大值。以 `mud.physics`、`hornet.physics`、各晶兽品种 `*.physics` 作总入口，嵌套记录 `spatial.tick`、`nav.*`、`crowd.*`、`ground.move`、`attack_area.*` 等。另有 `attack_starts.<兵种>`，每次真正走进攻击起手上报一次，不抽样；**它不是命中次数**。各层的包含子调用时间**禁止累加**。

汇总：

```powershell
python tools\analyze_enemy_perf.py D:\MFGG_Perf\normal\perf_play_<stamp>_frames.csv --output D:\MFGG_Perf\normal_summary.json
python tools\analyze_enemy_perf.py D:\MFGG_Perf\cpu\perf_play_<stamp>_frames.csv --output D:\MFGG_Perf\cpu_summary.json
```

将两份 summary JSON 与原始 `enemy_cpu.csv` 对齐解读；如果用户可以直接提供两个目录压缩包，诊断信息更完整。出于隐私，日志不保存玩家账号、存档、键位、截图或精确移动轨迹。

## 根因判断门槛

1. 先把 `enemies=0`、`1–9`、`10–19`、`20–29`、`30+` 的墙钟帧耗、P95/P99 和补步数分开；确认降帧与真实敌人数量的相关性。
2. 从 `30+` 慢帧中比较 `physics_steps==1` 与 `>=2`；排查“物理补算引起长帧、长帧又引起补算”的循环，同时审查同帧 draw/primitive 激增。
3. 对照 CPU 采样根入口，找出单个物理步中脚本成本占比，并在父子方法之间识别大头；对照 `attack_starts`，保证开关下仍然出招。
4. **只有测出具体路径才修改执行架构**。一旦针对某条路径改动，在相同场景进行 A/B，并运行 `tests/test_creature_navigation_and_attacks.gd`、`tests/test_enemy_attack_queue_hosts.gd`、`tests/test_navigation_moving_target.gd`、`tests/test_combat_spatial_navigation.gd` 等原有守卫。已知 `test_combat_spatial_navigation.gd` 在当前基线上有两条晶兽坡面失败 I-354，需同基线复现，不把失败默默忽略。
5. 若无 Godot 引擎环境，不宣称已通过解析、自动测试、回归或实机达到60FPS；PR保持 Draft，等待真实证据。

## 快速阅读结果

- `wall_frame_ms` 是实际渲染帧间隔；`engine_delta_ms` 不是可直接替代它的真实计时。
- `physics_steps>=2` 显示补步，但并非卡顿原因的直接证明。
- `TIME_PHYSICS_PROCESS` 包括物理阶段的脚本+引擎工作，不能等同纯碰撞成本；`TIME_PROCESS` 与它不是可相加的互斥两项。
- CPU 方法计时包含被调用的子方法，且只抽样每8个物理步；使用 **单次平均值、最大值与调用次数** 排序，不跨层求和，也不拿插桩后的FPS宣布性能提升。
