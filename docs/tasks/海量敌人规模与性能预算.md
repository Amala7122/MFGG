# 海量敌人规模与性能预算

## 目标与当前问题

用户 2026-10-12 要求继续分析与优化 `godot-ruin_star_new`，第一步先确定：按当前第三人称射击、开阔战场与敌人体型，**同一画面内多少敌人足以形成「海量」感**。本任务后续再把视觉目标换算为场上活跃总量、近身交战量和性能预算；未经用户确认，不直接提高正式刷怪上限。

用户 2026-10-13 进一步确认：**100 个真实敌人是必须做到的硬约束**，不再作为可下调的远期愿望。首个完整一局不继续打磨当前主场景的机器人普通敌人；六种新敌人直接作为百体新核心的正式兵种目标，避免先接旧框架再迁移。沉积泰坦作为单个关底 Boss，走独立完整实体，不计入普通敌人批量核心的 100 个体预算。本轮仅更新实施边界，尚未开始新核心或正式替换。

本任务遵守「分析可以宽、执行必须窄」：数量不是预设答案，先用正式相机与正式敌人做可重复对照；寻路、物理、渲染、战斗和联机容量分别计量，不把视觉目标直接等同于全功能实体数量。

## 已核对的当前基线

- 正式模式为 `spawn.mode = waves`；场上密度目标 `target_alive = 14`、同时存活硬上限 `max_alive = 18`。
- 当前流程只启用 `sanctum`；地图 `extent = 90 m`，刷怪锚点距中心约 `26–60 m`。
- 玩家使用 5 m 弹簧臂、垂直 FOV 70° 的近距第三人称相机，默认窗口 1920×1080。
- 普通敌人基础碰撞体约 1 m 宽、1.9–2.0 m 高，图鉴体型倍率约 0.65–1.75；数量增加后会同时改变遮挡、目标可读性与近战拥堵。
- 已有 256 个体导航计量证明正式完整导航远未达到 60 FPS，但那是「全体完整 CharacterBody3D + 正式导航链」的容量事实，不能反推视觉上需要 256 只。

## 100 个正式敌人的受控性能结果

最终采用的 A/B 条件：Godot 4.7.2、Ryzen 5 5600X、RTX 5060 Ti、高画质、圣所、12:00 晴天；实际截图 1920×1080，1152×648 为 UI 逻辑画布（本轮修正上一轮误报）；正式投放算法与等级 4 图鉴配比，预热 300 帧后测量 900 帧。两组人口全程稳定，均无意外退场。`process` 与 `physics` 是引擎监视器各自口径，不能据此拆分纯脚本/纯物理，也不能相加当总帧耗。探针固定模拟步进，数字是该诊断窗口的墙钟帧耗，正常时间步进的实跑另验。

| 指标 | 当前上限 18 只 | 目标 100 只 | 变化 |
|---|---:|---:|---:|
| 平均墙钟帧耗 | 10.106 ms | 46.975 ms | 4.65× |
| P95 / P99 帧耗 | 14.346 / 16.331 ms | 59.000 / 70.377 ms | P95 4.11× |
| 平均 FPS / 1% low | 98.9 / 61.2 | 21.3 / 14.2 | 平均下降 78.5% |
| 超过 16.67 / 33.33 / 50 ms 的帧 | 6 / 0 / 0 | 900 / 898 / 236 | 100 只几乎全程达不到 30 FPS |
| `process` 平均 | 9.61 ms | 25.53 ms | 2.66× |
| `physics` 平均 | 8.63 ms | 44.13 ms | 5.11× |
| 平均绘制调用 | 927 | 2132 | 2.30× |
| 平均图元数 | 553,385 | 806,805 | 1.46× |
| 结束节点数 | 2,616 | 9,021 | 3.45× |
| 视锥内敌人数均值 / P95 | 9.9 / 12 | 42.6 / 53 | 高峰进入海量区间 |
| 导航队列 P95 / 最大 | 2 / 3 | 42 / 51 | 队列显著堆积 |
| 规划延后次数 | 0 | 68 | 开始触发预算拥塞 |

**受控测试能支持的结论**：当前实现的 100 只平均 21.3 FPS，898/900 帧越过 30 FPS 预算。它不能支持「硬件跑不动 100 个完整敌人」或「必须以装饰群体替代真实敌人」；上轮提前推荐减少完整实体缺少架构对照，2026-10-12 本轮纠正。代码复核还确认正式敌人的 `collision_layer=4 / collision_mask=3` 已排除彼此实体碰撞，不能继续把敌人互撞列为已存在瓶颈。100 个完整可交互敌人仍作为研究目标，先以成熟导航与简化运行框架对照，再决定是否需要共享、分频或数据化。

受控证据：[18 只报告](../../../_artifacts/godot-ruin_star_new/horde_performance_18_controlled/20261012_202317_c4b1e325/reports/horde_performance_018.json)、[100 只报告](../../../_artifacts/godot-ruin_star_new/horde_performance_100_controlled/20261012_202418_31499cd4/reports/horde_performance_100.json)。前期未固定天气的运行只作为探针调试；一次 100 只复跑人口从 100 偶发降至 32，已登记 I-096，不用其缩水后的帧率作为容量结论。

## 最新反馈与独立架构审查

用户反馈：「100个性能不够只能说是架构不行，这套电脑配置绝对不至于跑不动100个敌人。先研究一下改架构怎么改，我的意见是从零点出发，不受项目现状影响，独立审查分析，必要的话完全推倒重来。」本轮授权为架构研究，新增的运行代码均为隔离诊断入口，正式游戏脚本、场景与参数未改。

本轮读取成熟原生导航、流场、局部避让、批量渲染与服务器 API 资料，并核对真实代码。明确推荐：重建敌人运行核心与模型/材质组织，使用原生路径服务、简化运动核、集中群体/接战管理、共享呈现；保留全部 100 个真实个体。共享流场与全面 ECS 保留作经计量触发的扩容路线，不把已有框架或已投入工作量当成保留理由。

最小反证已完成：

- 100 只正式模型/动画/攻击接到独立原生路径后，平均诊断帧耗 30.076 ms，原生路径查询平均约 0.434 ms/帧；相对原链 46.975 ms 显著下降，但完整目标仍未达标。
- 关闭敌人攻击后 28.082 ms，再关闭程序动画后 25.479 ms，再隐藏敌人显示后 15.551 ms；这些只是消融诊断，不能把功能关闭后的成绩当作验收。
- 独立基础移动核仍使用全部 100 个正式 CharacterBody3D 与世界碰撞，100 次 `move_and_slide()` 合计均值 2.505 ms/物理步。其场景为静止目标汇聚后，未代表持续移动/复杂通道；已足以否定把 44 ms 监视器数值直接归因于 CharacterBody 本身。
- 全部有效组全程保持 100 个；关闭动画探针的首轮类型错误已修复并复跑，失败报告不用于结论。
- 实际 PNG 确认窗口输出为 1920×1080；新增图像尺寸字段，登记导航高度不匹配 I-097 与尺寸接口误报 I-098。

完整比较、职责、体型/楼层/能力边界、迁移阶段、设计预算和反证场景见 [百体敌人架构设计](../features/百体敌人架构设计.md)，该文档的证据链接对应本轮真实产物。

下一步建议为独立新核心的验证实现，再接回代表兵种的合并呈现与完整战斗；本轮未实现新核心，未证明正式 100 只达 60 FPS，未验证移动玩家、多层/门洞/动态地形、100 只全部入镜和战斗峰值，也不自行标记观感验收。

交付核对：本轮五组有效图形诊断的导入与运行均通过、全程人口稳定；目录完整性检查通过，设计稿与任务中的本地产物链接有效。单个失败诊断已保留并在设计稿中说明，不混入有效测量。

## 正式相机视觉结论（首版）

固定条件：圣所出生机位、玩家相机 70° 垂直 FOV（16:9 下水平约 102.4°）、俯角 12°；敌人在镜头前 15–52 m、左右各 39° 的扇区内按确定性网格打散，外观循环使用正式图鉴；场景时间冻结，六档截图唯一变量是数量。

| 画面内敌人 | 观察结论 |
|---:|---|
| 18 | 分散的小规模交战，与当前 `max_alive=18` 一致；没有连续敌阵，不构成海量 |
| 32 | 明显繁忙，接近「大群」；轮廓仍以单体为主，场地空白占比高 |
| 48 | 左右与纵深开始形成连续敌阵，是当前画面第一次稳定跨入「海量」的下沿 |
| 64 | 不用依赖特效或夸张聚团也能明确读成海量；仍保留道路、掩体和兵种轮廓，是常规目标的最佳平衡点 |
| 96 | 强烈的压境/高潮感；敌人名称与生命文本开始大面积叠字，单体与威胁来源的可读性明显下降 |
| 128 | 数量继续增加，但规模感收益已明显递减；主要增加遮挡和文本噪声，不适合作为常态画面目标 |

**首版推荐**：当前单人玩法把 **48–64 个画面内敌人**定义为「海量」即可；常态瞄准 **64**，高潮可短时到 **80–96**，不需要追求 256 个同时出现在镜头里。正式生成器会优先在镜头外或遮挡后投放，且 102.4° 水平视野只占完整环绕的约 28%；敌人追击后会向玩家聚集，因此初步把单人场上活跃总量目标放在 **96–128**，而不是直接按几何比例推到 225。这个换算仍是待真实运动回放验证的假设，不是已验收容量。

四人合作不能简单把单人数字乘四：四人抱团时可共享同一批敌人，分散行动时才接近每名玩家一份局部密度。当前正式玩法只有单人流程，所以本轮不把 320–480 之类的多人上限写成开发目标。

视觉对照同时暴露了 I-093：64 只开始出现名称/生命文本遮挡，96/128 只时已经严重重叠。要把 64 只作为正常目标，敌人头顶信息必须按距离、瞄准对象、受伤状态或精英身份做显示预算；不能继续让所有敌人常驻完整文本。

证据：[_artifacts 固定对照报告](../../../_artifacts/godot-ruin_star_new/horde_density_capture_fixed/20261012_195517_af912d42/reports/horde_density.json)，截图位于同一运行的 `screenshots/horde_density/`。第一轮未冻结天气的截图只作为探针调试，不作为最终对照。

## 验证与边界

- 截图必须由正式场景、正式相机和正式敌人生成；探针只在隔离项目里运行，不修改正式配置。
- 静态截图用于判断视觉规模，不代表运动群聚、音效、攻击密度或实际帧率；这些是后续独立步骤。
- 用户没有明确确认前，不把任何数量标记为最终满意，也不据此更改 `target_alive` / `max_alive`。
- 固定对照运行 import 与图形探针均通过；六档请求数、生成数与相机视锥内数量完全一致。目录：`_artifacts/godot-ruin_star_new/horde_density_capture_fixed/20261012_195517_af912d42/`。
