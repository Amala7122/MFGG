# 百体敌人架构：独立审查与重建建议

状态：2026-10-12 研究稿。普通导航与成本拆分已实测；新架构尚未正式实现，性能与行为尚未验收。执行记录沿用 [海量敌人规模与性能预算](../tasks/海量敌人规模与性能预算.md)。

## 1. 从玩法目标定义问题

用户要求「100 个性能不够只能说是架构不行」，并明确要求从零出发、项目现状不限制方案、必要时建议完全重建。研究目标因此是 **100 个真实、独立、可交互的敌人**，每个保留身份、生命、受击、追击和攻击能力。不能把其中大部分换成不能受击的装饰个体，再宣布达标。

默认设计验收目标为同一台 5600X + 5060 Ti、1920×1080、高画质下稳定 60 FPS；这个帧率是工程目标，尚未得到新实现保证。100 个场上活跃个体和 100 个全部入镜分别测试，不能用只有 40 多个入镜的结果替代绘制最坏情况。当前单人是首个验收场景，未来多目标需要独立测量。

完整敌人需要保留的功能与计算方式分开定义：

- 移动、世界碰撞、受击响应和攻击时序保持固定物理步进。
- 选目标、战术位置、感知和全局重画路径可以按事件或较低频率更新，并分摊到不同帧。
- 可见敌人仍有动画；动画、网格、材质的组织可全部重做。
- 飞行、跳跃、攀爬、破障若为某兵种能力，分别实现，普通步行不支付所有能力搜索成本。
- 不能为了通过性能测试，让不可达平台被穿越、敌人长期停住、地图外个体静默消失或真实人口缩水。

地图主问题是三维场景上的地面行走、坡面、门洞和局部高差；它适合三维导航网格。重叠楼层必须保留层与拓扑，不能仅按 XZ 高度图处理。真正自由飞行才需要另一种空间表达。

## 2. 先修正基线解释

之前测试证明当前实现代价高，不能证明硬件只能承受少量完整敌人。上轮「必须减少完整实体、靠装饰群体补量」的结论撤回。

还有三条口径修正：

1. 正式敌人 `collision_layer=4 / collision_mask=3`，本来不碰撞彼此。把敌人互撞当现存瓶颈没有依据；拥堵首先是缺少分离与接战组织。
2. `TIME_PHYSICS_PROCESS` 包含物理步进期间执行的游戏逻辑，不能直接当作 Jolt 或 `CharacterBody3D` 本身的耗时；`TIME_PROCESS` 也不能当成纯脚本耗时。监视器不是互斥分项，且部分数值延迟更新。[Godot 性能监视器](https://docs.godotengine.org/en/stable/classes/class_performance.html)
3. `get_visible_rect()` 的 1152×648 是 UI 逻辑画布；旧、新 PNG 文件头都确认实际截图 1920×1080。纹理尺寸 getter 在本轮返回 3200×1800，不能据此认定 GPU 在渲染这个尺寸；已记录 I-098，上游有 [相似接口错误](https://github.com/godotengine/godot/issues/110922)。所有最终验收必须记录窗口、实际图像与 3D 渲染比例。

现有探针使用 `--fixed-fps 60`，真实墙钟时间可用于同条件成本比较，但模拟时间会与墙钟脱离。它是诊断窗口，不能替代正常时间步进的实时游玩验收。下表 FPS 仅为墙钟渲染帧率。

## 3. 新做的独立对照

没有更改正式 `scripts/`、场景或配置。原生对照在隔离副本中，用 [horde_native_steering.gd](../../tools/probes/horde_native_steering.gd) 替换导航接口。继承原类型仅为接入已有敌人，实际运行逻辑独立：原生网格路径、每只缓存路点、目标变化阈值、0.25 秒查询门槛，直接沿路点移动。全部 100 只仍是正式 `CharacterBody3D`，保留原模型、程序动画、近战/远程攻击和特效。

随后依次关闭敌人攻击、程序动画和敌人显示，只用于区分成本。不同运行的追击轨迹、聚团和入镜数量会变化，均值差不能直接视为精确的互斥函数耗时，也不能相加保证新架构收益。

原生完整组在 900 帧内执行 1930 次 `map_get_path`，总时间 390.169 ms：每次约 0.202 ms，平均每个诊断帧约 **0.434 ms**。这里包含原生查询的端点处理。换成共享流场最多能节省其中一部分，不能拿它解释或消除剩余约 30 ms 的整帧代价。

模型隐藏组仍计算实体位置和世界碰撞，成绩只说明呈现成本值得重建。它关闭了功能，不能当作「100 完整敌人已达 60 FPS」。原生对照也尚无局部避让、楼层正确性、防坠落与特殊能力验收；远近战移动不再遵守旧规划器全部规则，不能直接部署。

最后一组还绕开正式敌人的整个逐帧行为回调，独立移动核直接给正式身体施加速度、重力、地面吸附，并每步调用一次 `move_and_slide()`。测量的 900 个物理步中，**全部 100 个身体的 `move_and_slide()` 合计平均 2.505 ms/步，整个群体移动循环平均 2.662 ms/步**。这是静止目标汇聚后的基础碰撞成本，不包含完整玩法，也没有测最坏的持续运动/门洞；它足以反证「44 ms 物理监视器意味着 100 个 CharacterBody 本身就要花 44 ms」，不能用来承诺任何地图/动作下都只有 2.5 ms。该组目标静止，预热后路径不再重画，因此测量期 `native_queries=0` 是预期现象。

探针启用后没有远离玩家超过 10 m 且长停的近战，旧链同条件有 9 个；这仅是此静止玩家窗口的观察，不能代替持续移动、门洞与不可达目标测试。

## 4. 当前实现为何容易随数量放大

以下是代码事实与机制判断，不是把整帧减去某个计数器后猜剩余成本。

### 4.1 地图通行证明重复放进普通运行时

每只角色持有 `NavSteering + NavigationAgent3D + CombatSpatialController`。普通地面 profile 只有 WALK，但仍进入完整能力规划框架。

- `CombatSpatialController.tick()` 每只做自身与目标支撑查询、可攻击姿态、地形高度关系、路线有效性及退出证明；目标是同一玩家时，许多目标信息仍逐只重复计算。
- `SpatialRoutePlanner.walk_route()` 先验证直行；失败后才查询网格，随后再次逐段落地和完整身体验证，还会尝试两种路径后处理。
- `SpatialQuery.ground_segment()` 按约 0.45 m 采样，细化时约 0.15 m；每段可能叠加射线、形状重叠、扫掠及跨坎验证。
- `NavigationPath → NavArcShape` 的圆角、重采样、形变与终检继续对形状路径做验证。
- 执行时 `gate_motion()` 与真实 `move_and_slide()` 又负责支撑与碰撞。

这些证明在能力原型中有用途，但让每只普通兵持续支付整条链，缺少清晰的成本上界。新体系把静态可走性、净空、坡度放进地图生成阶段，运行时保留局部世界碰撞和必要的边缘检查。

这样做的前提是地图表达可信。当前烘焙高度 2.0 m，却存在实际高 3.5 m 的普通近战（I-097），因此不能简单删验证而保留不匹配的网格。必须同时修正体型分类与导航净空。

### 4.2 普通行走承担了异常能力与路径造型成本

路径搜索、身体证明、攻击站位、脱困、坑沿退出、跳跃/攀爬/破障与弧线造型耦合。缺少路线时也要经历较重判断，规划队列堆积后又放大目标过期与重画。

新的普通路径只解决可走区域中的路线。能力移动另有明确入口、退出点、动作状态和中断规则；动作发生时验一次必要条件。平滑转向是运动表现层需求，优先用转向限制与短程前瞻，不把整条路线重采样/逐段物理证明作为常规前置。

### 4.3 外形组织不适合批量呈现

当前两类敌人由几十个独立网格组成，外观部件还会新建网格与材质。`EnemyRig` 在物理步进内修改节点链的变换，并做远程右臂 IK；`EnemyVisuals` 收集每只模型上的局部材质实现染色与闪白。原生完整组绘制调用均值约 2519，网格组织和材质共享必须一起审查。

Godot Forward+ 的自动实例化要求共享网格与材质；每实例参数可表达独立颜色/闪白而无需复制材质。是否能自动合批仍受网格、材质、透明方式、皮肤等条件影响，需要实测，不承诺共享材质就自动把所有角色变成一个 draw call。[3D 性能与自动实例化](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html)、[每实例着色器参数](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/shading_language.html#per-instance-uniforms)

## 5. 从零可选的四种方案

| 方案 | 成熟基础与收益 | 成本、失败条件与反证 | 本轮判断 |
|---|---|---|---|
| A 保留全部控制链，做缓存/降频/预算修补 | 功能与现有测试迁移少，短期可逐点省成本 | 普通走路仍承担复杂能力证明；查询、执行、攻击耦合；难以给出可执行的最坏帧预算；独立原生对照已说明其中相当多运行逻辑可以替换 | 保留作回归参考，不作为百体主架构 |
| B 原生导航 + 简单运动核 + 集中群体管理 + 合并呈现 | 原生路径搜索与世界碰撞可直接使用；普通兵行为清晰；仍保留 100 个真实实体；路径层已测到约 0.43 ms/诊断帧 | 必须补匹配体型的导航数据、群体分离、能力连接、动态地形和呈现转换；现有模型/战斗代码原样接回仍有 30 ms，不能只换路径接口 | **首选，重建敌人核心与呈现组织** |
| C 分块共享流场 + 局部避让 + 数据化个体 | 大量同目标角色共用反向代价场；单位从场采样方向；适合更大人群与共享目标 | 活跃目标、体型与楼层越多，共享场越多；移动目标要处理失效与分块更新；2D 展平可能错误连接桥上下；局部拥堵/世界碰撞/动画仍要处理；当前原生搜索仅 0.43 ms，首做流场收益不足 | 保留扩容接口，在搜索实测变成瓶颈时选用 |
| D 完整 ECS/服务器模拟 + 自建运动 + GPU 批量动画 | 数组组织、批量更新和渲染能显著减少节点与语言调用；适合后续更大规模 | 要重建命中、实体 ID、世界碰撞、动作、资源释放、编辑器观察、状态同步；线程化还受场景树/物理查询限制；如果保留原来的高频证明，换语言仍重复做同样的昂贵工作 | 作为经证据触发的升级路径，100 只阶段不先支付全部工程成本 |

成熟流场参考是 Elijah Emerson 对《Supreme Commander 2》的分块实现：代价场、积分场、流向场及区域连接。[作者章节](https://www.gameaipro.com/GameAIPro/GameAIPro_Chapter23_Crowd_Pathfinding_and_Steering_Using_Flow_Field_Tiles.pdf)。这支持其适用机制，不提供本项目帧率保证。

路径跟随与局部避让是两个问题；Recast/Detour 的 crowd 系统也分别管理路径走廊、邻域转向和避让，接入时还有位置控制权等约束，不能把它当作免集成的通用插件。[Detour Crowd](https://recastnav.com/group__crowd.html)

完整 ECS 或 Server API 是合理候选，但 Godot 官方把绕开节点树的服务器方案放在大规模逐帧对象的优化路径上；当前既有证据还不能证明必须淘汰 100 个 CharacterBody3D。[Godot Server API](https://docs.godotengine.org/en/stable/tutorials/performance/using_servers.html)

## 6. 推荐架构的职责与更新方式

| 模块 | 唯一职责与输出 | 运行方式 |
|---|---|---|
| EnemyWorld | 个体 ID、生命、阵营、位置、速度、兵种与动作状态 | 集中注册；状态有唯一所有者 |
| TargetService | 玩家状态、目标位置/所在导航面与公共感知数据 | 每物理步共享快照；死亡/传送即时事件 |
| RouteService | 根据体型/能力和地图版本提供普通路点与能力连接 | 路径缓存；目标/地图变化事件；分帧发起原生查询 |
| CrowdService | 邻域分离、目标附近接战位置、狭窄入口通行 | 空间索引，限制近邻数；与地图楼层/通行面一致 |
| MovementMotor | 把期望速度变为实际位移，处理地面、台阶、击退 | 60 Hz；每只每步一个主要移动入口；按受阻条件触发额外处理 |
| CombatDirector | 攻击意图、预警/锁定/命中/收招、出手机会与目标检测 | 时间与事件驱动；只对实际有机会命中的对象查询 |
| EnemyPresentation | 模型、骨骼动画、材质实例参数、标签与特效 | 从状态读取；允许独立绘制/动画频率，不能反向改变战斗事实 |

### 6.1 普通路线与地图

以合理体型组生成导航地图或过滤层，而不是为每只重验全地图，也不为每只分别烘一张。类必须同时覆盖半径、高度、坡度和台阶限制；只有半径分组不足以证明头顶净空。身体能力与导航类别必须能从项目配置核对。

原生查询返回部分路径时区分「已到玩家」和「只能到路线末端」，避免无条件直线回退。复用查询参数与结果，错开重画；不每帧设置新目标或先重复查询一次可达性。[查询对象复用](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationpathqueryobjects.html)、[导航优化纪律](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_optimizing_performance.html)

多层位置使用导航面/区域/连接信息，不用单一 XZ 距离跳过同平面投影但实际不同楼层的路点。本轮原生适配器按 XZ 推进只是成本诊断，不是正式多层实现。

静态地图结构由建图保证；可破坏物通过局部地图/连接版本使受影响路径失效。碰撞仍挡住角色，世界改变后不靠过期地图把身体硬推过去。出生投放可以做一次完整安全校验，其成本和每帧追击分开。

### 6.2 群体分离与接战

空间哈希/分格索引只查询局部近邻，避免每只扫描所有其他敌人。初版可测试 8–12 个近邻上限，参数是实验起点，不是已验收最优值；楼层不同的重叠 XZ 个体不能相互排斥。

先比较简单分离与 Godot 原生 RVO。RVO/ORCA 修正局部速度，不取代全局路径或世界碰撞；其理论与示例效率也不能直接作为包含本游戏动画/战斗的整帧成绩。[ORCA 原始研究](https://gamma.cs.unc.edu/ORCA/)

目标附近的站位、攻击机会与后排推进由 CombatDirector/CrowdService 组织，使角色分散、让出入口、避免全部重叠到同一坐标。所有个体持续存在、可受击、可换目标；同时出手数是玩法压力参数，不能用它冒充运行容量优化。群体目标并不要求恢复已淘汰的单环/多环追击方案。

### 6.3 动画和网格

首选同兵种共享网格与材质，普通人形尽量合为一个蒙皮主体、少量装备节点；使用 Skeleton3D 的骨骼表示动作，颜色/闪白使用实例参数。必要的程序姿态/IK 保留为明确的骨骼修正，按可见性与动作需要计算。

模型参数仍可在观察台调节：编辑参数改变后重新生成对应 profile 的网格并缓存，实例沿用同一生成结果。不能因为合并模型就丢掉参数与身体部位对应关系，也不能把可调外形复制成另一份预览实现。

若保留刚性分部件风格，也可比较「共享部件几何/材质 + 批量骨骼/部件变换」；先量化它与单个蒙皮主体的提交和变换成本，再选。没有必要先换美术风格。

MultiMesh/VAT 是更大规模的候选：它能批量绘制，但普通 MultiMesh 不会自动提供每个实例独立 Skeleton3D；需要动画纹理或骨骼数据方案、实例级命中映射与分区裁剪。[MultiMesh 官方机制](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)。即使采用批量显示，每个实例仍可以对应一个真实战斗 ID。

### 6.4 特殊能力、战斗与信息

跳跃、攀爬、破障和飞行具有独立状态及进入条件。能力连接只描述可选路线，不负责执行动作；起跳前检查落点/连接状态，过程中处理击退、死亡和世界变化。[NavigationLink 的执行边界](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationlinks.html)

命中判定与范围预警网格分离。攻击按真实预警/锁定/命中时点查询；地面特效可缓存、池化或异步更新，不能为了画预警把整个可达性证明塞回普通导航。

生命数字、名字、伤害飘字使用显示规则与复用对象，优先瞄准者、精英、受击者。I-093 的标签遮挡和 I-094 的相机堵塞要独立验收；遮挡镜头时淡出挡镜模型/部件的显示策略也应和命中实体分开。

## 7. 推倒范围与实施顺序

推荐的是 **新建敌人核心，而不是继续延长现在的全能控制器**。不是因为旧代码量大，而是普通路线、能力证明、运动、战斗与呈现的责任边界本身不合适。

可直接复用的东西按产品需要判断：关卡、兵种数据、属性方案、动作/攻击设计、美术形状、玩家武器和独立命中契约。它们不要求用现有敌人内部框架。重做敌人核心和网格组织能覆盖已测主要问题；重做存档、菜单、地图美术等目前没有额外性能收益证据。

建议落地阶段：

1. 在独立验证入口建立 100 个真实胶囊的原生路径、世界移动与反证场景；可重复指定种子、数量、行为和地图，不以旧规划器内部字段当新功能要求。
2. 定义目标共享快照、体型导航类别、普通路径缓存、唯一移动入口；接入局部分离与接战组织。性能低于目标时先定位具体函数/引擎阶段。
3. 用一个代表兵种制作合并模型与共享材质对照，扩展到 100 个可见、不同动画相位的角色，确认收益和外形可调能力。
4. 接回近战/远程兵种差异、真实攻击特效、受击、击退、死亡；每次接入都测增量，不能把最后一轮结果从空壳成绩外推。
5. 接回确实需要的特殊移动与动态地形；在最终入口使用正常时间步进的实跑验收。
6. 达标后替换正式敌人入口；旧模块明确退出正式链，只保留有用途的对照。若清晰的真实实体运动核仍超预算，再依据函数计量选择数组化/GDExtension/Server API，或依据路径搜索占比引入共享流场。

## 8. 明确预算与反证

设计起点：敌人侧 CPU 目标约 5–7 ms/物理步，其中原生普通路径约 1 ms、运动/局部避让约 2–3 ms、战斗与感知约 1 ms、动画/呈现准备约 1–2 ms。不同统计可能重叠，最终必须用互斥计时或主线程/GPU 时间线核对。这些是预算分配，不是当前实测，也不承诺各项都能一次做到。

整个项目的 CPU 与 GPU 分别预算，不能把所有 16.67 ms 留给敌人，也不能把 CPU 与 GPU 相加作为整帧公式。先测空场/玩家基础成本，再给群体系统留出真实余量。

必须验收：

- 开阔地、持续移动/折返/传送目标、狭窄门洞、坡脚台阶、不可达高台、多层上下重叠、破坏物变化。
- 100 活跃与 100 入镜；近身拥堵、远程弹幕峰值、群体受击和连续死亡回收。
- 人口、有效追击与出手、非战术停滞、穿墙/坠落、路径查询、邻居数、每层耗时及峰值。
- 正常时间步进，高画质实际 1920×1080，记录物理 TPS 与模拟秒/墙钟秒，防止通过减慢游戏或减少个体得到好帧率。

推荐的完成门槛为稳定 60 FPS、P95 帧耗 ≤16.67 ms、P99 尽量 ≤20 ms，同时行为用例通过；最终值由实跑和用户试玩确认。只拿到平均 FPS 不足以验收。

仍未知：新呈现方案的精确收益、真实角色持续运动和复杂通道的最坏成本、局部避让品质、多个导航体型的地图成本、移动目标与动态地形峰值、全部角色入镜且攻击同时发生的上界。这些未知不妨碍推荐 B，但妨碍宣称 B 已经达标。
