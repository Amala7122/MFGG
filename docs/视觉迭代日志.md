# 视觉迭代日志

> 每一轮都必须回答两个问题：**画面比上一轮更接近目标了吗？** 以及
> **新增的东西改善了「轮廓 / 构图 / 视觉层级 / 空间纵深」里的哪一条？**
> 答不上来的改动一律不做。

> **注意（2026-09-19）**：本项目的服务器联机与本地分屏功能已整体移除，仅保留单机。
> 下文凡涉及「分屏 / 联机大厅 / 救助提示 / 小队面板」的段落均为历史记录，相关 UI 与代码已删除。

## 加法否决闸（每轮逐项打勾）

| 检查项 | 含义 |
| --- | --- |
| 轮廓 | 物体外形更清楚、更能一眼读出来了吗？ |
| 构图 | 大形的位置关系更有秩序、更有引导性了吗？ |
| 视觉层级 | 明度 / 饱和 / 大小的主次更分得开了吗？ |
| 空间纵深 | 近 / 中 / 远的区分更强了吗？ |
| 结论 | 以上四条一条都答不上来 → 这项不改 |

同时必须通过玩法契约自检：**地形最大坡度 ≤45°**、**掩体高度 2.2~2.6m**、**导航多边形数 > 0**。

## 复核方式（每轮固定）

```
D:\godot_project\Godot_v4.7.1-stable_win64_console.exe --path D:/godot_project/godot-zelda -- --vis-capture --vis-round=<N>
```

固定竞技场 `lakefront`、固定窗口 1600×900、固定等待 150 帧、隐藏 UI、三个固定机位：

- `wide` 看天空构图与远景色层
- `ots` 看中景与近中对比
- `near` 看近景轮廓清晰度

产出 `visual_captures/<N>_<机位>.png` 与 `<N>_report.txt`。

## Round 0 — baseline（动手之前的基准）

契约自检：地形最大坡度 **34.2°**（红线 45 ✔）／掩体 **28 个，最高 2.60m** ✔／导航 **1163 个多边形** ✔／MeshInstance3D **112**

### 差异最大的三个问题

#### ① 天空是一张没有任何结构的浅灰纸（最严重）

- 天空占画面 40~50%，从顶到地平线几乎只有极轻微的明度渐变，**没有云层、没有分层、没有明暗块**。
- 色相偏**暖紫灰**，不是要求的冷灰蓝。
- 地平线处没有亮带，无法给地景轮廓提供高对比底板。
- 直接后果就是用户说的那句：「如果还是均匀浅灰天空，那么地面怎么改都会像 Demo」。参考图有一半风格来自天空，所以它排在第一位。

#### ② 完全没有空间纵深

- 0–50m 与 500m+ 的对比度、饱和度、色温几乎一致：`fog_density = 0.004` 只是一层均匀白纱，把远近一起冲淡。
- `fog_aerial_perspective` / `fog_depth_curve` 全仓搜索结果为 0 —— 一个都没启用。
- 地形边界是一条**笔直的矩形切边**（`wide` 图里可见地平线是一条完美直线，下面直接是雾色），把「这个世界是一块 120×120 的板」暴露无遗。
- 视野里没有任何巨型轮廓，40% 以上的画面是空天空。

#### ③ 没有尺度感

- 画面里所有人工物都在 5m 以下：遗迹立柱 `r≈0.5m × h=5m`、掩体 2.4~2.6m 的细长盒子、树 3.6m。
- 28 个尺寸接近的盒子均匀散在地面上，读起来是「随手扔的积木」，不是「厚重石构」——正是用户点名的「小房子 × 40」症状。
- 神龛那颗青色发光球是画面里最亮的东西之一，把视觉焦点从地景轮廓上偷走。

### 另外记录（本轮不改，按优先级排队）

- **明度结构是反的**：掩体 `(0.49,0.47,0.4)` 比地面草绿更亮，于是石构读成「亮积木」；树冠绿 `(0.12,0.4,0.11)` 与地面绿 `(0.19,0.46,0.16)` 几乎同明度 → 树在地面上**读不出剪影**。
- **饱和过高**：草绿在 `saturation 1.12` 加成后远超「低饱和灰蓝／暗灰绿／灰褐／冷石色」的要求；路面暖褐与湖岸暖黄进一步把画面推向「卡通白天」。
- **几何语言不统一**：巨石是 16×10 段的光滑 UV 球（画面里唯一圆滑的东西）；树是两个球叠成的「花生」；草叶是 0.28m 细盒，在画面上读作噪点而非植被。
- **湖是硬边矩形平面**，直接切在地形上（`near` 图右下角可见明显的直角梯形色块与蓝色水面）。
- 导航烘焙有一条既存警告：`PARSED_GEOMETRY_MESH_INSTANCES` 会在运行时把视觉网格从 GPU 读回 CPU（`navigation_region.gd:37`）。新增视觉内容时要注意**不要塞进 `nav_source` 组**。

### 本轮判点

Round 1 只做用户指定的两件事：**程序分层天空** 与 **分段空气透视**。上面「另外记录」里的明度 / 饱和 / 几何全部留到后续轮次，避免一次改太多。

## Round 1-4 - 大气层

### 做了什么

新增 `shaders/procedural_sky.gdshader`，三段垂直分层加纯数学噪声云，零贴图。

扩展 `graphics_director._apply_sky()`：原实现有一句 `is ProceduralSkyMaterial` 判断，换了自定义材质后四张竞技场的天空预设会**静默失效**（不报错、只是不生效）。现在两种材质都认。

先在真实 4.7 上探测了 `Environment` 属性名，确认 `fog_mode` 支持 `FOG_MODE_DEPTH`，配 `fog_depth_begin` / `fog_depth_end` / `fog_depth_curve` 才是真正的「分段」雾，比指数雾精确得多。代码统一加了一道属性存在性检查：属性名写错在 Godot 里不会报错，只会静默不生效，那是最难查的一类失效。

**关键发现：体积雾是遮住天空的元凶。** 实测 `presets.high.volumetric_fog`（密度 0.012 / 长度 120m）不是「阳光光柱」，而是一层被暖色太阳照亮的均匀纱：近景整体提亮、远景被冲淡、天空被整片盖成暖灰。已全部关闭。

**还有一处判断被实测推翻**：原以为远景蓝灰化要调高 `fog_sky_affect`。实测它控制的是「雾遮住天空的程度」，调高会让天空重新变成一块均匀灰 —— 恰恰是要避免的结果。远景蓝灰化应交给 `fog_aerial_perspective`（让远景取天空自身的辐射色）。

### 中轴取样对比（wide 机位，V = 明度 / S = 饱和度）

| | Round 1 暖灰纱还在 | Round 4 最终 |
| --- | --- | --- |
| 天空顶部 | 0.70 暖 (0.70,0.67,0.64) | 0.53 冷 (0.33,0.41,0.53) |
| 天空中部 | 0.69 | 0.64 |
| 地平线 | 0.71 | 0.82 |
| 远景剪影 | 无 | 0.22 |
| 地面 | 0.64 | 0.25 S=0.09 |

天空从「无结构的暖灰」变成「冷蓝灰 + 0.53 到 0.82 的明度阶梯」；地面从 S=0.47 的亮绿变成 S=0.09 的暗冷灰绿。亮天空 / 暗地景的明度结构第一次成立。

### 否决闸打勾

- 轮廓 ✔ 远景出现 V=0.22 的连续剪影带，此前完全被雾吃掉
- 构图 ✔ 天空有了从上到下的明度骨架
- 视觉层级 ✔ 天空最亮、地景最暗
- 空间纵深 ✔ 0-50m 干净、远景向天空色收敛

### 剩下的三个问题

1. **云仍然偏弱**：覆盖与明暗都在涨，但还没形成「巨大的明暗构图」。
2. **地形边缘仍是软糊的矩形切边**，暴露「世界是一块 120×120 的板」。
3. **没有任何巨型体量**：画面里最高的东西是 5m 的细圆柱。

## Round 5~12 - 背景地台与巨型地标

### 做了什么

新增 `scripts/backdrop_landmark.gd` + `scripts/lowpoly_mesh.gd`（几何工厂）+ `scripts/world_backdrop.gd`（autoload 挂载）。

- **背景地台**：从竞技场边缘（56m）铺到 900m 的大切面盘，半径按指数拉开，远处面更大。它消掉了地形那条笔直的矩形切边——「世界是一块板」不再暴露。
- **巨型地标**，全部由 Cube 组成，只靠尺度说话：2 段 15m 断裂高墙、3 根 30m 方柱、1 座 60m 门框、3 座 150m 塔体（各自带基座）。
- 60m 门框**固定放在主路延伸方向的灭点上**，这是「构图」这一项的直接落地。

### 契约

- 导航多边形数 **1163，与没有地景时逐值相同** —— 无碰撞体、不入 `nav_source` 组，对 Jolt 与导航烘焙零影响，已实测确认。
- 新增绘制调用 **2 个**（地台 ArrayMesh + 地标 MultiMesh），分屏双视口下共 4 次。

### 否决闸打勾

- 轮廓 ✔ 地平线上第一次出现可辨认的巨型剪影
- 构图 ✔ 门框落在主路灭点，画面有了纵深轴
- 视觉层级 ✔ 远景体量比天空暗、比近景亮，层级清楚
- 空间纵深 ✔ 地台 + 分级色 + 分段雾共同建立 0→900m 的连续纵深

### 本轮踩到并记录的两个坑

1. **顶点色与 `albedo_color` 的色彩约定不同。** `albedo_color` 按 sRGB 转线性，顶点色默认被当作线性直读。同一串 0.13 走两条路差了近一个数量级，表现是「地台用地面色却亮成了沙滩」。修法：`vertex_color_is_srgb = true`。
2. **`fog_density` 在 `FOG_MODE_DEPTH` 下不参与计算。** 把它从 0.85 改到 0.35 画面毫无变化；饱和距离完全由 `fog_depth_end` 决定。最初把 `depth_end` 设成 620m，恰好卡在地标距离上，最远那座 150m 塔被冲到比天空还亮（"远景发光"）。改成 1200m 后，620m 处只到 27% 雾，塔体恢复成冷灰蓝剪影。这条已写进 `game_config.json` 的 `_fog_mode_doc`。

### 剩下的三个问题

1. **地形仍是一块平滑的绿色板**，没有任何大切面 —— 这是 Round 4 的核心任务。
2. **掩体与道路仍是地面最亮最暖的东西**，和「暗色冷灰」的整体调子脱节。
3. **云仍偏弱**，天空的明暗构图有了但不够强。

## Round 13~18 - 地图与程序解耦

### 做了什么

新增 `scripts/world_map_builder.gd`：按 `arenas.definitions.<id>.map` 建造道路 / 水体 / 陈设 / 光源 / 树簇，全部经 `height_at()` 吸附。四张图各自写了 `map` 段，并把场景里写死的 Roads / Lake / AncientRuins / EnemyCamp / Forest **退役**（`use_legacy_props: false`，改一行就能切回）。

**从此新增一张地图只需要在 JSON 里加一段 `map`，不必碰代码或场景。**

同时修掉三处审计查出的硬耦合：

- `player_spawner.gd` 的 `SPAWN_ORIGIN` 迁到 `map.spawn_origin`（原先它只对得上湖畔的出生圆，另外三张图的玩家会生到圆外、脚下是斜的）
- `enemy_spawn_point.gd` 与 `survival_director.gd` 里写死的世界边界 `48.0` 和湖盒四个数字，改为读地形范围与 `ArenaUtil.is_masked_out()`
- `ArenaUtil.validate()`（写了很久但**全仓零调用**）接到启动自检上

### 自检抓到的第一个真问题（既存缺陷）

接上自检后立刻报出：**采石场地形最大坡度 57.1°、废墟内城 56.0°，都超过 `agent_max_slope = 45°`**。那片坡对敌人等于不存在，而画面上完全看不出来。

根因找到了：钟形剖面 `(1-d²)²` 最陡处斜率是 `1.539 × 山高 / 半径`，而椭圆山的**短轴可以只有长轴的 0.6**。生成器一直只拿长轴做安全校核，短轴方向的坡因此悄悄超标。修法是按短轴反推山高上限（山可以矮，但不能陡）：

| 竞技场 | 修前 | 修后 |
| --- | --- | --- |
| 湖畔遗址 | 34.2° | 34.2°（用显式 hills，未受影响） |
| 采石场 | 57.1° ✘ | **39.6° ✔** |
| 废墟内城 | 56.0° ✘ | **42.1° ✔** |
| 风蚀沙丘 | 24.0° | 24.0° |

诊断路上试错了两次，值得记下来：先怀疑遮罩过渡带（把 margin 从 4 加到 14，**毫无变化**），又怀疑生成器缩山时只缩半径不降高度（改了等高比缩放，也**毫无变化**）。两次都说明"最陡点不在遮罩边、也没触发缩放路径"。最后靠"坡度要按短轴算"这条几何事实才定位到。

## Round 30~33 - "黑成一片"：环境光静默失效的排查

**症状**：圣所背光面与切面阴影塌到接近全黑（`north_high y=0.83` V=0.06、`orbit_ne y=0.94` V=0.07、`gate_low y=0.39` V=0.11），明度层级被吃掉，与"阴天而非欠曝"的目标相反。

**误判过程（值得记）**：怀疑环境光太弱，连抬 `ambient_energy` 1.35 → 1.65 → 2.4、`fill_energy` 0.55 → 0.75 → 0.9。Round 32 与 Round 30 取样**逐值相同**，说明这些改动全是静默无效。

**Round 33 调试确认**：`sun_energy=1.55 fill_energy=0.9 ambient_energy=2.4` 已正确载入，`env.ambient_light_energy=2.4`、`env.ambient_light_source=3 (SKY)` —— 配置没读错，但画面纹丝不动。

**根因**：场景 `Environment` 的 `ambient_light_source = SKY`，而 Godot 默认 `ambient_light_sky_contribution = 1.0`。当它 = 1.0 时，环境光 **100% 取自天空**，`ambient_light_color` / `ambient_light_energy` 两个参数**完全不参与**（文档原文：ambient light parameter has no effect）。于是所有 `ambient_*` 调参从头到尾都是空的。

## Round 34 - 根因修复并验证

`graphics_director._apply_ambient()` 里，只要 preset 提供了 `ambient_color` 或 `ambient_energy`，就先 `env.ambient_light_sky_contribution = 0.0`，再套用这两个参数。没配 ambient 的图保持原样不动（可能继续用天空驱动）。

修复后第一次真正生效，背光面/阴影面全部抬回可读区间，而受光面与天空纹丝不动（环境光只补阴影、不冲亮面）：

### 否决闸打勾

- 轮廓 ✔ 背光面的切面明暗分级回来了，不再读成一块黑
- 构图 ✔ 阴天亮面/暗面的关系成立，天空仍是最亮层
- 视觉层级 ✔ 阴影从 0.06~0.11 抬到 0.20~0.27，与黑石材（0.16~0.22）分出层级
- 空间纵深 ✔ 环境光整体上抬但不冲天空，远中近关系不变

### 剩下的问题 / 待复核

1. **`ambient_energy = 2.4` 是"追亮度"阶段在 bug 未修时推到的高值**，现在才是它第一次真正生效。数值本身可用（阴影 0.20~0.45 不灰不黑），但需要人眼看一眼实图确认是否偏灰，若偏灰可降到 1.6~2.0。
2. **中央黑石台（`south y=0.50` V=0.17）与两侧 `y=0.50` 暗带（V=0.22）没被环境光提亮** —— 这是材质本身暗（`stone_dark`），不是光照失效；是否符合"暗但不黑"需人眼定夺，若仍太黑就把 `stone_dark` 反照率单独抬一点。
3. **此修复是全图生效**：四张旧图的 `ambient_color/energy` 在重新启用时会首次真正接管环境光（此前同样静默无效）。临时关闭期间无需处理，但重新启用时要各自复核 —— 尤其 `dunes` 的 ambient 偏低偏暖（0.6 × 暖色），可能让沙丘阴影比修前更暗。

### 本轮踩到并记录的两个坑

1. **`ambient_light_sky_contribution = 1.0` 让 `ambient_*` 全部静默失效。** 属性名没写错、数值也读进去了、`env` 里也显示是新值，但画面纹丝不动 —— 这是"最难的静默失效"那一类。修法：手动 ambient 前先把天空贡献归零。
2. **`--vis-arena` 换图受 `arenas.order` 约束。** `ArenaUtil.resolve_id()` 只认 `order` 数组里的 id，其余一律回落 `order[0]`。当前 `order=["sanctum"]`，所以 `--vis-arena=lakefront` 拍了照样是圣所。换图验证前要先把 id 加回 `order`。

## Round 35 - 菜单补上石板：把"拼凑感"改成"同一套 UI"

**症状**：HUD 已经是一套切角石板（Round 以前几轮统一到 `UiThemeUtil.draw_plate`），但主菜单 / 暂停 / 结算 / 大厅**是直接压在半透明暗幕上的一堆 Label**。玩家进游戏的第一屏恰恰就是主菜单，所以"原型感"十有八九先从这儿来。

### 改了什么

| 改动 | 为什么 |
| --- | --- |
| 新增 `scripts/menu_panel.gd` | 四种屏幕共用一块石板，只换强调色。它 **extends PanelContainer**：容器负责按内容撑开，把 `panel` 样式盒换成空盒保留内边距，绘制权就完全归 `_draw` —— 于是"自动排版"与"形状自己画"两件事同时成立 |
| 新增 `scripts/tracked_label.gd` | `Label` 画不出字距，而"小号 + 宽字距"是不引入字体资源的前提下让默认字体看起来被设计过的最省力手段。HUD 早就有 `draw_tracked` 这个原语，菜单却还是普通 Label —— 同一款游戏里出现两种"小标题"，正是拼凑感的来源 |
| `game_flow` 收成单个 `_present()` | 原先三个 `_enter_*` 各写一遍动画/显示代码，改一处要改三处。`_present(副标题, 强调色, 提示行, 统计)` 之后，屏幕之间只差文案与数据 |

| 按钮错开 40ms 淡入 | 一次性静止出现读起来是"一堆控件"；有先后地把视线从上往下带一遍，读起来才是"一屏菜单" |
| 主题新增 `LineEdit` 样式 | 大厅那三行地址 / 房间码原先是 Godot 系统默认的**浅灰圆角框**，一块深色石板中间嵌着三个浅色圆角矩形 —— 全项目最出戏的一处，比按钮没样式更显眼（面积大、颜色浅，直接在暗幕上发光） |
| `BossBar` 出场由中间甩开 | 首领出现之前没有任何预警，而血条是"打起来了"的第一个信号。直接出现在那里，玩家会以为自己漏看了开场 |
| `ReadoutPlate.pulse_on_change` | 只有击杀数打开：生存时间每秒变几十次，开了会一直抖 |

| --- | --- | --- |
| 主菜单 | 728×**608**（窗口 648，余量 40） | 隐藏 |
| 暂停 | 728×452 | 3 块，无重叠 |

### 本轮踩到的坑

1. **截图脚本按帧数等是错的。** 帧率不定（有窗口被垂直同步限制，无头全速跑），按 50 帧等到最后一张时补间只跑了 0.76 —— 拍出来是一张"大厅全黑"的图。改成**轮询"所有 MenuPanel 的 `modulate.a` 是否回到 1"**，而不是数帧。

### 剩下的问题 / 待复核

1. **主菜单只剩 40px 余量**（608 / 648）。正文再加一行就会溢出；为了塞下已有的石板，本轮删掉的都是同义重复（"生存模式"说两遍、"如何输入"说三遍）。**人眼需要确认现在的信息密度是否够** —— 如果还要加说明，先把石板改成两栏（左：模式说明 + 关卡选择，右：操作表），而不是继续缩字号。

3. `GameFlow._build_arena_row()` 只在主菜单构建选关行，**暂停时不清理**（这是既存问题，本轮补了 `_clear_arena_row()`）。
4. `theme/game_theme.tres` 与 `scripts/ui_theme.gd` 两份终于统一了（`ui_theme` 改为返回 `UiThemeUtil.build_default_theme()`），并且 `PlayerHUD` / `GameFlow` 都改走缓存版本 —— 但**.tres 仍需人工与代码同步**，新增样式那一刻别忘了把它补回去。

## Round 36 - HUD 顶部两处重叠：中央那一列也得在【横向】避让

**症状**（用户截图）：顶部中央的「阶段 1 寂石圣所」横幅左端伸进了左上角的生命面板，把护盾读数整块盖住。

### 根因

`PlayerHUD` 的分层注释里只有一张**纵向**槽位表（生存 22..56 / 波次 60..96 / Boss 100..146），而这一列的元素（生存读数 / 波次横幅 / Boss 血条）都是"占满整行"的宽元素。横向宽度原先按**屏幕宽的 ±340** 算：

| 元素 | 改前 | 与左栏的关系 |
| --- | --- | --- |
| 波次横幅 | 236..916 | 压住生命面板（28..300）**64 像素** |
| Boss 血条 | 276..876 | 压住生命面板 **24 像素**（纵向 100..110 也交叠） |

纵向排得再整齐也挡不住横向伸长 —— 这是"只按宽度改纵向"的思路漏掉的一整个方向。

### 修法

新增 `_center_half_width(width, narrow)`：这一列的半宽由**两侧留白**算，不由屏幕宽算。

约束是两条：左端不能让过左栏（生命面板 28..300），右端不能让进右栏（小地图 958..1126）。

```gdscript
guard = TOP_ROW_GAP + maxf(VITALS_LEFT + VitalsPanel.PANEL_WIDTH,    # 左栏右边界 300
                           Minimap.MARGIN + Minimap.PANEL_SIZE)      # 右栏左边界 194
half  = width * 0.5 - guard                                          # 1152 → 268
```

取**两个留白的较大者**而不是各算各的边界：这样这一列仍然屏幕居中，与上面同样居中的生存读数对齐；各算各的会把它推得偏右，两行错开半个身位。

### 顺带一起解决的

- **帧数读数压进小地图 2 像素。** 它是 `Label`，最小高度由字体撑到 26，压不住 22 的槽位（实际矩形被顶到 2..28，而小地图从 26 开始）。改挂到击杀读数下面 —— 那里下方直到武器面板都是空的，向下长多少都不会撞。
- **右上角那一列原先由两个函数各摆一半**（`_layout_top_hud()` 与 `relayout_for_width()`），改成 `_place_right_column(narrow)` 一处，顺手删掉 `_layout_top_hud()`。
- **技能读数在窄屏下会撞右下角武器面板**（那 248 宽是固定值）：现在它的右边界同时受屏幕与武器面板夹。
- 删掉 `WaveBanner.HALF_WIDTH`：它是第二份宽度真相，改了不生效，只会误导。

### 复核方式

临时探针跑一局真实战局，把每个 HUD 控件的实际矩形全打出来并两两求交：

| 视口 | 结果 |
| --- | --- |
| 1152×648（标准） | ✓ 无重叠。波次横幅 308..844，Boss 条 308..844 |
| 880×648（窄屏） | ✓ 无重叠 |
| 720×648（窄屏） | ✓ 无重叠 |

### 本轮踩到的坑

**探针"跑了但没测到"。** 第一版用 `root.size = Vector2i(880, 648)` 缩窗口来测窄屏，三组输出**逐值相同** —— 项目用的是 `canvas_items + aspect=expand`，逻辑宽度被锁在 1152，缩宽度只是把多出来的部分变成高度（可见矩形变成 1152×848）。窄屏分支根本没被触发。必须**同时**改 `content_scale_size` 才能真的走到那条分支。

顺带发现：`NARROW_WIDTH`（<900）这条分支在当前的 stretch 配置下**由拖窗口永远触发不到**（可见宽度恒 ≥ 1152），只有分屏 SubViewport 或以后改 stretch 配置才用得上。仍然修好了它 —— 但它不是"我会遇到"的路径。

## Round 37 - 删掉窄屏分支：它是"走不到的那条路"，而且它骗了人

上一轮最后那条发现引出的问题：一条永远走不到的分支，留着不只是脏 —— 它让人以为
"HUD 会自适应宽度"，于是 Round 36 那个重叠恰恰在它的注视下发生了。用户确认窄屏已废弃
（现在分屏与单人就是同一比例），本轮整体删除。

### 删了什么

| 删除项 | 说明 |
| --- | --- |
| `NARROW_WIDTH` + `relayout_for_width` 里的 `narrow` 分支 | 整条紧凑排布（生存读数挪左栏、中央列下移、击杀读数再下移一层） |
| `SURVIVAL_COMPACT_*` / `*_TOP_NARROW` / `SQUAD_TOP_NARROW` | 只服务窄屏的槽位常量，共 8 个 |
| `_center_half_width(width, narrow)` 的 `narrow` 参数 | 现在只有一种算法 |
| `_place_right_column(narrow)` 的参数 | 同上 |
| `_hook_resize()` | 见下方"为什么要连它一起删" |
| `_abilities_label` 的宽度夹取 | 1152 下 `minf(360, 1124, 866)` 恒等于 360 —— 纯空操作，改回建的时候写死 |

`_squad_panel` 原先靠重排那一遍摆位，现在回到 `_add_squad_panel()` 里就地定位 ——
"建立即就位"比"建完再补一次坐标"少一条心智负担。

### 为什么要连 size_changed 订阅一起删

原本觉得该留着兜底。查了对面的 `split_screen.gd` 才确认：**宿主的最终宽度在进入分屏那一刻就定了**
（`content_scale_size` 设成 `1152 × 座位数`、`aspect` 切成 `KEEP`），之后不会再变。实测每块分屏
SubViewport 是 **1151×648**，这一辈子不会再换。所以那条订阅连响一次的机会都没有，而它带来的错觉是
"宽度变了会自动纠正" —— 正中 Round 36 的坑。

现在的重排入口只剩两个：`setup()` 一次；换宿主时 `split_screen._adopt_hud()` 显式喊一次
`player.refresh_hud_layout()`。**这一条现在是唯一入口，注释已在两侧都写明。**

顺带把 `split_screen.gd` 里三处引用 `NARROW_WIDTH` 的注释改写了 —— 其中那条
"HUD 会在 0 宽下摆一次、size_changed 会纠正"的理由已经不成立了：没有订阅兜底之后，
`viewport.size` 的初值从"省一次重排"变成**不可省**。

### 复核

| 项 | 结果 |
| --- | --- |
| 单人 HUD 九块控件两两求交 | ✓ 无重叠，坐标与清理前逐值相同 |
| 本地双人两块分屏 | ✓ 视口各 1151×648，两侧 HUD 的波次横幅都是 308..843（**按 1151 算出来的**，证明 `refresh_hud_layout` 在宿主尺寸定了之后才跑） |
| lint / 无头启动 | 全绿 / 无报错 |

## Round 38 - 两条玩法修复：冲锋枪无限子弹 / 救助提示搬到救助者自己的屏幕上

### ① 冲锋枪子弹无限，"备弹池"降级成"备用弹夹"

**症状**：备弹 180 发打完就再也换不了弹（原 `start_reload` 里有一条 `_reserve <= 0` 的
早退），而备弹只能靠子弹包补 —— 包捡不到时玩家彻底失去攻击手段。那是**无解局面**，不是难度。

按用户给的规则重做主武器弹药：

| 规则 | 实现 |
| --- | --- |
| 主武器子弹无限 | 换弹永远成立；备用弹夹为空时直接给一个满弹匣（`get_capacity()`，含弹匣模块加成） |
| 子弹包直接压进弹夹，上限 300 | 不变（`weapon.magazine_ammo_max`） |
| 多余的进备用弹夹，上限 300 | `add_ammo` 在弹匣压满后把剩余量写进 `_reserve`，受 `reserve.primary_max` 约束 |
| 超过 30 发不能换弹 | 保留 `_ammo >= get_capacity()` 早退 |
| 上弹优先上备用弹夹 | `_finish_reload` 一次尽量取满（`min(备用, 上限 - 当前)`），不再只补到容量 |

关键的一条是"一次尽量取满"：备用弹夹里可能攒着几百发（都是子弹包溢出来的），
如果一次换弹只让装 30 发，那些存货要反复换十次才用得上 —— **存进去容易、取出来难，等于不存在**。

顺带删掉 `emergency_trickle`（每秒回一点备弹的防卡死机制）：现在"保底满弹匣"是结构性保证，
它成了纯冗余；配置里的 `emergency_trickle_per_second` 一并去掉。

**HUD 上有一处必须跟着改**：`备弹 0` 原本会转红，注释写着"打完这匣就没子弹了，不可逆"。
这条前提已经不成立 —— 继续转红会传递一个假警报。改成"备用 N"，恒为暗色。

### ② 救助提示：只在倒地者头顶有，救助者自己屏幕上没有

**复现结论**：强制把队友打到 0 血、再走过去，倒地者头顶那块 Label3D **是正常显示的**
（`state=1`、`near=true`、文本"按住 F / LB 扶起"）。所以机制没坏 ——
坏的是**它长在错误的地方**：

- 它是世界空间的 Label3D，**挂在倒地者身上**，会被他自己的身体与倒地信标的光柱挡住；
- 救助者的视线在准心与敌人身上，不在队友头顶；
- 更关键的是救援半径只有 **2.6 米**，在交战距离感里非常近 ——
  站在 4 米处的玩家看到的世界和站在 40 米处一模一样，只会以为功能坏了。

**改法**：提示搬到【要按那个键的人】自己的 HUD 上（底部居中，青色 20 号），分三档：

| 距离 | 提示 |
| --- | --- |
| > 注意范围（9 m） | 不显示 |
| 注意范围内、救援范围外 | `队友倒地　再靠近 3.4 米` |
| 救援范围内（2.6 m） | `按住 F / LB 扶起`，正在扶则显示 `扶起中 42%` |

中间那一档是这次真正解决问题的部分：**告诉玩家"差多少"**，而不是让他在两个状态之间盲猜。

同时把头顶提示与自己 HUD 的提示收成同一个常量 `REVIVE_KEY_HINT`（按键名写两处迟早漏改一处），
并在 `_refresh_life_state()` 里补一句：自己倒下时立刻收掉提示 ——
`_update_revive()` 在倒地期间不再被调用，不收就会一直挂在自己屏幕上。

### 复核（临时探针，16 项全过）

| 组 | 结果 |
| --- | --- |
| 弹药 | ✓ 备用 211 + 弹匣 28 → 一次换弹变 239，备用清零 |
| | ✓ 备用为 0、弹匣打光 → 保底 30；再换一次仍然 30（无限生效） |
| | ✓ 弹匣满不触发换弹；子弹包先进弹匣、溢出进备用；两仓都满返回 0（不消耗掉落物） |
| 救助 | ✓ 40 m 不显示；6 m 显示"再靠近 3.4 米"；1.2 m 显示按键 |
| | ✓ 倒地者自己不显示"去救别人"的提示 |

### 本轮踩到的坑

探针第一版报了"两仓都满时返回 30（应为 0）"——**是探针自己写错了**（只把弹匣填满、
备用仓还留着 200 的余量，溢出根本不会发生）。先把被测对象改对再怀疑测试，
但也不能反过来无条件信测试输出：这一条是"测试写错"而不是"代码写错"，
靠把前置条件打印出来才看清。
